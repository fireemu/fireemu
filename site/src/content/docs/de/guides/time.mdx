Fireemu hat eine eigene Uhr, und jeder Dienst liest sie: Server-Zeitstempel, Zeiten von Dokumenten und Objekten, Ablauf von Tokens, geplante Funktionen und `request.time` der Security Rules. Standardmäßig läuft sie mit Echtzeit, wie die Produktion. Legen Sie fest, wo sie startet, bewegen Sie sie oder frieren Sie sie ein, und jeder Dienst sieht die neue Zeit.

## Echtzeit folgen oder die Uhr einfrieren

| Konfiguration | Verhalten der Uhr |
|---|---|
| Kein `daemon.clockStart` (der Standard) | Folgt der Echtzeit ab dem Moment, in dem der Daemon gestartet wurde. |
| `daemon.clockStart` fixiert | Startet zu dieser Zeit und steht still, bis sie bewegt wird, was einen Lauf reproduzierbar macht. |
| `daemon.clock` auf `"realtime"` gesetzt | Eine fixierte Uhr läuft ab ihrem Start weiter. |
| `daemon.clock` auf `"frozen"` gesetzt | Eine nicht fixierte Uhr bleibt stehen. |

Eine Bewegung (`clock:advance`, `clock:advanceTo`, `clock:set` oder die Seite „Runtime“) ist ein Offset auf einer Uhr, die der Echtzeit folgt: Die Uhr läuft von dem Punkt aus weiter, an dem sie landet.

Eine virtuelle `functions.clock` (siehe [Anwendungszeit in Functions](#anwendungszeit-in-functions)) folgt dieser Uhr, was auch immer sie tut. Die Welten von `fireemu/testing` fixieren den Start, daher steht ihre Uhr still.

### Während der Daemon läuft umschalten

Die Konfiguration legt nur den Modus fest, in dem der Daemon startet. Zur Laufzeit schalten Sie mit **Freeze** / **Resume** auf der Seite „Runtime“ der [Emulator UI](../ui/) um, oder über die Control-API:

```sh
# Die Uhr beim aktuellen Zeitpunkt anhalten.
curl -X POST http://127.0.0.1:9099/v1/sessions/default/clock:freeze -H 'content-type: application/json' -d '{}'
# Ab dem angezeigten Zeitpunkt wieder der Echtzeit folgen.
curl -X POST http://127.0.0.1:9099/v1/sessions/default/clock:resume -H 'content-type: application/json' -d '{}'
# Zuerst auf die aktuelle Zeit springen, dann ihr folgen (Sync to real time auf der Seite „Runtime“).
curl -X POST http://127.0.0.1:9099/v1/sessions/default/clock:resume -H 'content-type: application/json' -d '{"syncToRealTime": true}'
```

Jede Antwort mit der Uhr und `GET /v1/sessions/default` enthalten `"running": true`, solange die Uhr der Echtzeit folgt, und `false`, solange sie eingefroren ist. Ein Fortsetzen zählt die Zeit nicht, in der die Uhr stand. `syncToRealTime` ist ein Setzen: Eine Bewegung zurück (ein festgelegter Start in der Zukunft) wird abgelehnt, außer der Body enthält auch `"allowBackwards": true`. Ohne Body ist es ein einfaches Fortsetzen; ein gesendeter Body muss ein JSON-Objekt sein (ein wörtliches `null` wird abgelehnt). Eine Uhr ohne Echtzeitquelle (die Welten von `fireemu/testing`) antwortet mit `400 FAILED_PRECONDITION`. Die Dienste des Daemons lesen die gemeinsame Uhr und sehen die Umschaltung, sobald die Anfrage zurückkehrt; geplante Funktionen, die während eines Sync-Sprungs fällig wurden, laufen wie nach `clock:advance`. Eine virtuelle `functions.clock` erreicht jeden Functions-Runner als Nachricht, und die Anfrage (über die API oder die Seite „Runtime“) wartet, bis die Runner sie haben (`503 CLOCK_NOT_SETTLED`, wenn einer nicht innerhalb von 10 Sekunden antwortet). Anwendungscode sieht `Date.now()` beim Einfrieren nie zurückgehen: Es bleibt beim zuletzt gezeigten Wert, bis die Uhr ihn überholt; nur ein Zurückstellen bewegt es zurück. Die Uhr gehört allen Sitzungen gemeinsam, daher gilt die Umschaltung für alle. Ein Snapshot-Restore stellt den erfassten Zeitpunkt wieder her und behält den aktuellen Modus. Die Startausgabe nennt den Startmodus und wie man umschaltet.

## Die Uhr um eine Zeitspanne oder auf eine Kalendergrenze stellen

Neben `{"seconds": n}`, `{"millis": n}` und `{"instant": "<RFC 3339>"}` können Sie eine Zeitspanne nach ISO 8601 angeben oder die Uhr auf den Anfang oder das Ende eines Tages, Monats oder Jahres stellen.

```sh
# 30 Tage später, einen Kalendermonat später, 36 Stunden später.
curl -X POST http://127.0.0.1:9099/v1/sessions/default/clock:advance -H 'content-type: application/json' -d '{"duration": "P30D"}'
curl -X POST http://127.0.0.1:9099/v1/sessions/default/clock:advance -H 'content-type: application/json' -d '{"duration": "P1M"}'
curl -X POST http://127.0.0.1:9099/v1/sessions/default/clock:advance -H 'content-type: application/json' -d '{"duration": "PT36H"}'
# Drei Tage zurück (zum Zurückstellen ist allowBackwards erforderlich).
curl -X POST http://127.0.0.1:9099/v1/sessions/default/clock:advance -H 'content-type: application/json' -d '{"duration": "-P3D", "allowBackwards": true}'
# Die letzte Mikrosekunde dieses Monats, dann im zweiten Beispiel der Beginn des nächsten Monats um 00:00 Uhr in Tokio.
curl -X POST http://127.0.0.1:9099/v1/sessions/default/clock:advanceTo -H 'content-type: application/json' -d '{"to": "endOfMonth"}'
curl -X POST http://127.0.0.1:9099/v1/sessions/default/clock:advanceTo -H 'content-type: application/json' -d '{"to": "startOfNextMonth", "timeZone": "Asia/Tokyo"}'
# Einen Monat weiter und dann auf den Anfang des Zielmonats.
curl -X POST http://127.0.0.1:9099/v1/sessions/default/clock:advanceTo -H 'content-type: application/json' -d '{"duration": "P1M", "to": "startOfMonth"}'
```

| Feld | Endpunkte | Wert |
|---|---|---|
| `duration` | `clock:advance` sowie `clock:set` und `clock:advanceTo` in Verbindung mit `to` | `P[nY][nM][nW][nD][T[nH][nM][nS]]` mit ganzen Zahlen und mindestens einer Komponente. Die Kennbuchstaben müssen großgeschrieben sein und in dieser Reihenfolge stehen. Ein führendes `-` zählt alle Komponenten rückwärts. Bruchteile sind unzulässig. Verwenden Sie für Zeitspannen unter einer Sekunde `millis`. |
| `to` | `clock:set`, `clock:advanceTo` | `startOfDay`, `endOfDay`, `startOfMonth`, `endOfMonth`, `startOfNextMonth`, `startOfYear`, `endOfYear` |
| `timeZone` | mit `duration` oder `to` | Ein IANA-Zeitzonenname wie bei einem Zeitplan. Ohne Angabe gilt `scheduler.defaultTimeZone`. Fehlt auch diese Einstellung, gilt UTC. |

Für die Berechnung gelten folgende Regeln.

- Jahre, Monate, Wochen und Tage ändern das lokale Datum und behalten die Ortszeit in der gewählten Zeitzone bei. Stunden, Minuten und Sekunden zählen die tatsächlich verstrichene Zeit. `P1D` folgt dem lokalen Kalender. Die verstrichene Zeit hängt vom Datum und von der Zeitzone ab. `PT24H` addiert immer genau 24 Stunden.
- Zuerst werden Jahre und Monate in Monate umgerechnet und zusammen angewendet. Fehlt der ursprüngliche Tag im Zielmonat, gilt dessen letzter Tag. Der 31. Januar plus `P1M` ergibt den 28. Februar (in einem Schaltjahr den 29.), der 29. Februar plus `P1Y1M` den 29. März. Danach folgen Wochen und Tage, zuletzt Stunden, Minuten und Sekunden.
- Bei gemeinsamer Angabe von `duration` und `to` wird zuerst die Zeitspanne angewendet.
- `endOfDay`, `endOfMonth` und `endOfYear` bezeichnen 23:59:59.999999 Uhr Ortszeit, die letzte Mikrosekunde des Tages, die ein Firestore-Zeitstempel darstellen kann. Wenn der Beginn des Folgemonats darstellbar ist und sich der Offset am Monatswechsel nicht ändert, liegt `startOfNextMonth` eine Mikrosekunde nach `endOfMonth`.
- Kommt eine Ortszeit beim Zurückstellen der Uhren zweimal vor, gilt der frühere Zeitpunkt. Auch ein Zeitplan läuft beim ersten Vorkommen. Entfällt eine Ortszeit beim Vorstellen der Uhren, gilt der UTC-Offset vor der Umstellung. Dadurch liegt der Zielzeitpunkt um die Dauer der übersprungenen Zeitspanne später. Bei einem Sprung von 02:00 auf 03:00 wird aus 02:30 also 03:30. Zeitpläne überspringen solche Zeiten. Eine Uhrbewegung braucht einen Zielzeitpunkt und folgt dafür der Regel `compatible` von `java.time`, Temporal und jiff.
- Das Ergebnis muss in den Jahren 0001 bis 9999 (UTC) liegen, ebenso jedes lokale Datum, das Jahre, Monate, Wochen, Tage oder der Ankerpunkt berechnen; Stunden, Minuten und Sekunden allein berechnen kein lokales Datum. Andernfalls wird die Anfrage mit `400 INVALID_ARGUMENT` abgelehnt.
- Liegt das Ziel vor der aktuellen Zeit, erfordern `clock:advance` und `clock:set` die Angabe `"allowBackwards": true`. `clock:advanceTo` lehnt die Bewegung wie bei `instant` ab.
- Alle drei Endpunkte geben 400 zurück und nennen die betroffenen Felder, wenn `seconds`, `millis` oder `instant` mit einem von `null` verschiedenen Wert für `duration`, `to` oder `timeZone` kombiniert wird. Ein neues Feld mit dem JSON-Wert `null` gilt als nicht angegeben. Ein Kalenderfeld, das der Endpunkt nicht unterstützt, führt ebenfalls zu 400, sofern sein Wert nicht `null` ist.
- Wie bei anderen Bewegungen enthält die Antwort die neue Uhrzeit im Format RFC 3339. Geplante Funktionen behandeln die Bewegung wie jede andere (siehe unten).

## Geplante Funktionen ausführen

Ein Zeitplan läuft, wenn die Uhr ein Vorkommen erreicht.

- Mit der Standarduhr geschieht das, während die Echtzeit vergeht.
- Bei einer eingefrorenen Uhr führt die Echtzeit nichts aus. Bewegen Sie die Uhr auf der Seite „Runtime“ der [Emulator UI](../ui/) oder mit der Steuer-API (`clock:advance`, `clock:advanceTo`, `clock:set`).

Jede Bewegung macht jedes Vorkommen in `(vorherige Zeit, neue Zeit]` fällig. Konfigurieren Sie Zeitzone, Nachholen und das Verhalten bei Überlappung im Abschnitt `scheduler`:

- `scheduler.catchUp` entscheidet, was läuft, wenn eine Bewegung mehrere Vorkommen überschreitet: `all` führt jedes aus (höchstens `scheduler.maxCatchUpRuns` pro Job und Bewegung), `latest` führt das neueste aus, und `none` führt keines aus.
- `scheduler.overlap` (`allow`, `skip`, `queue`, `reject`, `skip-in-flight`) entscheidet, was passiert, wenn ein Lauf fällig wird, während der vorherige noch läuft. Unter `strict` ist der Standard `skip-in-flight`, so wie sich Cloud Scheduler der Produktion verhält; unter `emulator` ist er `allow`.

Die Seite „Functions“ der UI kann eine geplante Funktion auch sofort ausführen oder die Uhr zu ihrem nächsten Vorkommen vorstellen. Ein manueller Lauf verbraucht das nächste Vorkommen nicht.

### Details zum Zeitplan

- Ein Vorkommen genau zur neuen Zeit ist in einer Bewegung enthalten, eines genau zur vorherigen Zeit nicht.
- Mit `scheduler.catchUp: all` bleiben Läufe über `scheduler.maxCatchUpRuns` pro Job und Uhrbewegung hinaus fällig und laufen, sobald wieder Platz ist. `latest` und `none` zeichnen pro Job und Uhrbewegung, die Läufe verwirft, eine Zusammenfassung `skipped: catch-up` auf.
- Ein Zurückstellen spielt nie erneut ab: Vorkommen, die der Zeitplan bereits passiert hat, werden nicht erneut ausgeführt, wenn die Uhr wieder über sie hinweg vorrückt, und der Zeitplan wird fortgesetzt, sobald die Uhr das letzte Vorkommen passiert, das er ausgeführt hat oder noch schuldet (sein Cursor). Nach einem Zurückstellen unter diesen Punkt bleiben noch geschuldete Läufe aus einem Rückstau oder wegen fehlenden Platzes zurückgehaltene Läufe geschuldet, werden aber nicht wieder fällig, bis die Uhr ihn passiert. Ein Sitzungs-Reset oder eine Snapshot-Wiederherstellung startet stattdessen jeden Zeitplan ab der aktuellen Zeit der Uhr, sodass nach einem Zurückstellen die Vorkommen zwischen dieser Zeit und einer späteren wieder fällig sind.
- `scheduler.overlap` gilt für Scheduler-Läufe und manuelle Läufe gleichermaßen, außer `skip-in-flight`, das einen manuellen Lauf nie ablehnt. Unter `skip-in-flight` (dem Standard von `strict`) wird ein Vorkommen verworfen (aufgezeichnet als `skipped: in flight`), solange ein Handler der Funktion, der vor der Uhrbewegung gestartet wurde, noch läuft, so wie es Cloud Scheduler in der Produktion tat, und die Vorkommen einer Uhrbewegung zählen nicht gegeneinander.
- Eine Funktion gilt als beschäftigt, solange einer ihrer Läufe in der Warteschlange steht oder läuft, einschließlich eines Laufs, der auf eine Wiederholung wartet; unter `skip` und `reject` kann daher ein noch ausstehender Wiederholungsversuch das nächste Vorkommen unterdrücken. Fireemu unterscheidet hier nicht zwischen einem Wiederholungsversuch und einem überlappenden Lauf. Mit `catchUp: all` überlappt sich eine Uhrbewegung über mehrere Vorkommen derselben Funktion selbst, sodass `skip` das älteste davon behält und `reject` den Rest als Ablehnungen zählt.
- Ist die Event-Warteschlange von Functions voll (4.096 aktive Events oder 64 MiB), bleibt ein fällig werdender geplanter Lauf fällig und läuft, sobald wieder Platz ist.

### Eine geplante Funktion jetzt ausführen

Ein manueller Lauf (`POST /v1/sessions/{session}/functions/{name}:run`) reiht einen Lauf einer geplanten Funktion ein, versehen mit der aktuellen virtuellen Zeit. Er verbraucht das nächste Vorkommen nicht, das weiterhin fällig wird und wie jeder Lauf `scheduler.overlap` unterliegt. Dies ist eine eigene Steuerfunktion von Fireemu, keine Aussage über das „Jetzt ausführen“ der Produktion.

| Antwort | Wann |
|---|---|
| `400 INVALID_ARGUMENT` | Eine unbekannte Funktion, eine Funktion, die nicht geplant ist, eine Ablehnung durch die Überlappungsrichtlinie oder eine Laufzeit, die gerade herunterfährt |
| `429 RESOURCE_EXHAUSTED` | Die Event-Warteschlange ist voll |

Bei einer Task-Queue-Funktion (`onTaskDispatched`) gibt dieselbe Route die Cloud-Tasks-Aufgaben frei, die auf ihre `scheduleTime` warten: alle oder die eine, die ein Body `{"task": "<task id>"}` benennt (404, wenn keine wartende Aufgabe diese ID hat). Siehe [Task-Queues](../../products/functions/#task-queues).

## Die Uhr rückwärts bewegen

Die Uhr kann sich rückwärts bewegen (`clock:set` mit `"allowBackwards": true` oder **Allow moving backwards** auf der Seite „Runtime“). Ein Zurückstellen spielt Vorkommen, die bereits gelaufen sind, nie erneut ab.

### ID-Tokens nach einem Zurückstellen

- Unter `strict` lehnen Authentication (`INVALID_ID_TOKEN`), Firestore und Storage ein ID-Token ab, das nach der neuen Zeit ausgestellt wurde, bis die Uhr seine Ausstellungszeit wieder erreicht.
- Im Profil `emulator` bleiben ID-Tokens nach einem Zurückstellen nutzbar, wie beim offiziellen Emulator, der ihre Ausstellungszeit nicht prüft.
- In beiden Profilen wird ein abgelaufenes Token weiterhin abgelehnt.

### Widerruf nach einem Zurückstellen

Ein Zurückstellen auf vor die Erstellung eines Kontos oder vor den Widerruf seiner Tokens lässt sogar das Token einer neuen Anmeldung als widerrufen gelten. Stellen Sie die Uhr stattdessen wieder vor oder setzen Sie die Sitzung zurück.

Umgekehrt widerruft ein Widerruf oder eine Passwortänderung nach einem Zurückstellen keine Tokens, die zu späteren Zeitpunkten auf der Zeitachse ausgestellt wurden: Das Profil `emulator` akzeptiert sie sofort, und `strict` akzeptiert sie, sobald die Uhr ihre Ausstellungszeit erreicht. Stellen Sie die Uhr vor dem Widerruf über deren Ausstellungszeit hinaus vor oder setzen Sie die Sitzung zurück.

## Zeiten, die dein eigener Code erzeugt

Manche Zeiten entstehen außerhalb von fireemu auf der Echtzeituhr des Rechners: Das Admin SDK setzt `iat` und `exp` eines Custom Tokens mit `Date.now()`, `getSignedUrl()` signiert eine Storage-URL mit der aktuellen Zeit, und `taskQueue().enqueue({scheduleDelaySeconds})` berechnet die `scheduleTime` der Aufgabe aus `Date.now()`. Ist die Emulatoruhr festgelegt oder verschoben (`daemon.clockStart`, `clock:advance`, jede `fireemu/testing`-Welt), weicht sie von diesen Zeiten ab. `daemon.callerTimes` legt fest, wie sie beurteilt werden:

- `clockOrWall` (Standard): Ein Custom Token oder eine signierte URL wird angenommen, wenn ihre Zeiten gegenüber der Emulatoruhr oder gegenüber der Echtzeit gelten. Eine `scheduleTime`, die näher an der Echtzeit als an der Aufgabenuhr liegt, behält ihre Verzögerung auf der Aufgabenuhr; mit `functions.clock.tasks = "virtual"` ist eine mit 60 Sekunden Verzögerung eingereihte Aufgabe nach 60 Sekunden Emulatorzeit fällig (und umgekehrt bei virtuellem `Date` mit `tasks = "real"`). Das ist eine Schätzung nach der nächstgelegenen Uhr: Liegen die beiden Uhren weniger als das Doppelte der Verzögerung auseinander, kann die Zeit näher an der Aufgabenuhr liegen und wird unverändert übernommen; geht die Aufgabenuhr 90 Sekunden vor der Echtzeit, ist diese 60-Sekunden-Aufgabe sofort fällig. Eine Ablehnung nennt die Emulatoruhr und die Echtzeit, zum Beispiel `INVALID_CUSTOM_TOKEN : the token's iat and exp hold neither against the emulator clock (2026-01-01T00:00:00Z) nor against wall time (…)`.
- `clock`: Jede solche Zeit wird nur gegenüber der Emulatoruhr beurteilt, so wie die Produktion gegenüber ihrer einen Uhr urteilt, mit den Meldungen der Produktion. `productionExact` wählt diese Einstellung.

```json
{ "daemon": { "callerTimes": "clock" } }
```

## Bei eingefrorener Uhr

Eine stehende Uhr lässt jeden Ablauf warten, bis du sie bewegst: Aktionscodes, SMS-Codes, ID-Tokens, Firestore-TTL und geplante Funktionen warten auf eine Bewegung der Uhr. Zwei Dinge sind anders:

- Pull-Abos von Pub/Sub führen Bestätigungsfristen und Wiederholungs-Backoff in Zustellzeit, die bei stehender Uhr mit der Echtzeit weiterläuft. Eine abgeholte, nicht bestätigte Nachricht kommt nach ihrer Bestätigungsfrist zurück, ein Nack unter einer `retryPolicy` nach dem Backoff, ohne dass die Uhr bewegt wird; das Vorstellen der Uhr bewegt beides weiterhin. Push-Abos halten ihren Backoff auf der Emulatoruhr: Stelle sie vor, um den nächsten Push-Versuch freizugeben. Wenn ein Push-Endpunkt bei stehender Uhr zum ersten Mal fehlschlägt, gibt der Daemon einen Hinweis aus.
- Der Widerruf vergleicht ganze Sekunden, wie in der Produktion: `revokeRefreshTokens` oder eine Passwortänderung in derselben Sekunde wie die Anmeldung lässt das ID-Token dieser Anmeldung gültig. In der Produktion wartet ein Test vor dem Widerruf eine Sekunde; bei eingefrorener Uhr stelle die Uhr zwischen Anmeldung und Widerruf um mindestens eine Sekunde vor. Bei einer solchen Uhr gibt der Daemon einen Hinweis aus, wenn ein Widerruf in die Sekunde der letzten Anmeldung des Kontos fällt.

## Anwendungszeit in Functions

Standardmäßig sieht Ihr Funktionscode die Echtzeit. Damit auch `Date.now()`, Timer und Cloud Tasks der virtuellen Uhr folgen, setzen Sie `functions.clock`. Ohne `daemon.clockStart` startet die Uhr zur Wanduhrzeit und folgt der Echtzeit, sodass `Date.now()` in Ihren Funktionen die aktuelle Zeit liest und virtuelle Timer nach ihrer Verzögerung auslösen, während die Echtzeit vergeht; eine Verschiebung verschiebt beides. Fixieren Sie zusätzlich `daemon.clockStart` für einen reproduzierbaren Lauf, bei dem die Uhr stillsteht, bis sie bewegt wird:

<Tabs syncKey="config-format">
<TabItem label="TOML">

```toml
# Configuration schema version: 1.
schemaVersion = 1

[daemon]
# Start the virtual clock at this date-time.
clockStart = "2026-01-31T23:59:00Z"

[functions]
# Directory of the Functions codebase.
source = "./functions"

[functions.clock]
# Functions date clock: "real" or "virtual".
date = "virtual"
# Functions timer clock: "real" or "virtual".
timers = "real"
# Cloud Tasks clock: "real" or "virtual".
tasks = "virtual"
```

</TabItem>
<TabItem label="JSON">

```json
{
  "schemaVersion": 1,
  "daemon": {
    "clockStart": "2026-01-31T23:59:00Z"
  },
  "functions": {
    "source": "./functions",
    "clock": {
      "date": "virtual",
      "timers": "real",
      "tasks": "virtual"
    }
  }
}
```

</TabItem>
</Tabs>

- Jeder Modus akzeptiert `real` oder `virtual`. Virtuelle Timer erfordern ein virtuelles `date`.
- Ist `tasks` auf `virtual` gesetzt, wird eine Cloud-Tasks-Aufgabe, die mit einer `scheduleTime` eingereiht wurde, fällig, wenn die virtuelle Uhr sie erreicht, sodass ein Test die Uhr vorstellt, statt zu warten.
- Ist `tasks` auf `real` gesetzt, wartet die Aufgabe unter `strict` auf die Wanduhr. Die Seite „Functions“ der [Emulator UI](../ui/) listet wartende Aufgaben auf und kann sie sofort ausführen.
- Eine Python-Codebasis sieht immer die Echtzeit: Sie wird nicht auf die virtuelle Uhr gelegt, und eine Konfiguration, die für den Functions-Runner ein virtuelles Datum verlangt, wird für sie abgelehnt.
