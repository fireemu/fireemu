Fireemu tiene su propio reloj, y todos los servicios lo leen: marcas de tiempo del servidor, horas de documentos y objetos, caducidad de tokens, funciones programadas y `request.time` de las Security Rules. Por defecto corre con el tiempo real, como lo hace producción. Establece dónde empieza, muévelo o congélalo, y todos los servicios ven la nueva hora.

## Seguir el tiempo real o congelar el reloj

| Configuración | Comportamiento del reloj |
|---|---|
| Sin `daemon.clockStart` (el valor predeterminado) | Sigue el tiempo real desde el momento en que inició el daemon. |
| `daemon.clockStart` fijado | Empieza a esa hora y permanece detenido hasta que se mueve, lo que hace reproducible una ejecución. |
| `daemon.clock` establecido en `"realtime"` | Un reloj fijado sigue corriendo desde su inicio. |
| `daemon.clock` establecido en `"frozen"` | Un reloj sin fijar se detiene. |

Un movimiento (`clock:advance`, `clock:advanceTo`, `clock:set` o la página Runtime) es un desplazamiento sobre un reloj que sigue el tiempo real: el reloj sigue corriendo desde donde queda.

<Tabs syncKey="config-format">
<TabItem label="TOML">

```toml
# Configuration schema version: 1.
schemaVersion = 1

[daemon]
# Start the virtual clock at this date-time.
clockStart = "2026-01-31T23:59:00Z"
# Virtual clock behavior: "realtime" or "frozen".
clock = "frozen"
```

</TabItem>
<TabItem label="JSON">

```json
{
  "schemaVersion": 1,
  "daemon": {
    "clockStart": "2026-01-31T23:59:00Z",
    "clock": "frozen"
  }
}
```

</TabItem>
</Tabs>

Un `functions.clock` virtual (consulta [Tiempo de aplicación en Functions](#tiempo-de-aplicación-en-functions)) sigue este reloj haga lo que haga. Los mundos de `fireemu/testing` fijan el inicio, así que su reloj permanece quieto.

### Cambiar mientras el daemon se ejecuta

La configuración solo fija el modo con el que arranca el daemon. Para cambiarlo en ejecución, use **Freeze** / **Resume** en la página Runtime de la [Emulator UI](../ui/), o la API de control:

```sh
# Detener el reloj en el instante actual.
curl -X POST http://127.0.0.1:9099/v1/sessions/default/clock:freeze -H 'content-type: application/json' -d '{}'
# Volver a seguir el tiempo real desde el instante que muestra.
curl -X POST http://127.0.0.1:9099/v1/sessions/default/clock:resume -H 'content-type: application/json' -d '{}'
# Saltar primero a la hora actual y después seguirla (Sync to real time en la página Runtime).
curl -X POST http://127.0.0.1:9099/v1/sessions/default/clock:resume -H 'content-type: application/json' -d '{"syncToRealTime": true}'
```

Cada respuesta con el reloj, y `GET /v1/sessions/default`, lleva `"running": true` mientras el reloj sigue el tiempo real y `false` mientras está congelado. Al reanudar nunca se cuenta el tiempo en que el reloj estuvo parado. `syncToRealTime` es un set: rechaza mover el reloj hacia atrás (un inicio fijado en el futuro) salvo que el cuerpo incluya también `"allowBackwards": true`. Sin cuerpo es una reanudación simple; un cuerpo enviado debe ser un objeto JSON (se rechaza un `null` literal). Un reloj sin fuente de tiempo real que seguir (los mundos de `fireemu/testing`) responde `400 FAILED_PRECONDITION`. Los servicios del daemon leen el reloj común, así que ven el cambio cuando vuelve la petición; las funciones programadas que vencieron durante un salto de sincronización se ejecutan como después de `clock:advance`. Un `functions.clock` virtual llega a cada runner de Functions como un mensaje, y la petición (desde la API o desde la página Runtime) espera a que los runners lo tengan (`503 CLOCK_NOT_SETTLED` si alguno no responde en 10 segundos). El código de la aplicación nunca ve retroceder `Date.now()` al congelar: se queda en lo último que mostró hasta que el reloj lo supera, y solo un retroceso lo mueve hacia atrás. El reloj es común a todas las sesiones, así que el cambio se aplica a todas. Restaurar un snapshot devuelve el instante capturado y mantiene el modo actual. La salida de arranque indica en qué modo empezó el reloj y cómo cambiarlo.

## Ejecutar funciones programadas

Una programación se ejecuta cuando el reloj alcanza una ocurrencia.

- Con el reloj predeterminado, eso ocurre a medida que pasa el tiempo real.
- Con un reloj congelado, el tiempo real no ejecuta nada. Mueve el reloj desde la página Runtime de la [UI del emulador](../ui/), o con la API de control (`clock:advance`, `clock:advanceTo`, `clock:set`).

Cada movimiento hace vencer todas las ocurrencias en `(hora anterior, hora nueva]`. Configura la zona horaria, el comportamiento de puesta al día y el de solapamiento en la sección `scheduler`:

- `scheduler.catchUp` decide qué se ejecuta cuando un movimiento pasa varias ocurrencias: `all` ejecuta cada una (como máximo `scheduler.maxCatchUpRuns` por job y movimiento), `latest` ejecuta la más reciente y `none` no ejecuta ninguna.
- `scheduler.overlap` (`allow`, `skip`, `queue`, `reject`, `skip-in-flight`) decide qué ocurre cuando una ejecución vence mientras la anterior sigue en marcha. Con `strict` el valor predeterminado es `skip-in-flight`, como se comporta Cloud Scheduler en producción; con `emulator` es `allow`.

La página Functions de la UI también puede ejecutar de inmediato una función programada, o avanzar el reloj hasta su siguiente ocurrencia. Una ejecución manual no consume la siguiente ocurrencia.

### Detalles de la programación

- Una ocurrencia exactamente en la hora nueva se incluye en un movimiento, y una exactamente en la hora anterior no.
- Con `scheduler.catchUp: all`, las ejecuciones que superan `scheduler.maxCatchUpRuns` por job y movimiento del reloj siguen vencidas y se ejecutan a medida que se libera espacio. `latest` y `none` registran un resumen `skipped: catch-up` por job y movimiento del reloj que descarta ejecuciones.
- Un retroceso nunca repite: las ocurrencias que la programación ya pasó no se vuelven a ejecutar cuando el reloj avanza sobre ellas, y la programación se reanuda cuando el reloj pasa la última ocurrencia que ejecutó o que aún debe (su cursor). Tras un retroceso por debajo de ese punto, las ejecuciones aún debidas de un atrasado o retenidas por falta de espacio siguen debidas pero no vuelven a vencer hasta que el reloj lo pase. Un reinicio de sesión o una restauración de instantánea inicia cada programación desde la hora actual del reloj, por lo que tras un retroceso las ocurrencias entre esa hora y una posterior vuelven a estar vencidas.
- `scheduler.overlap` se aplica por igual a las ejecuciones del scheduler y a las manuales, salvo `skip-in-flight`, que nunca rechaza una ejecución manual. Con `skip-in-flight` (el valor predeterminado de `strict`) una ocurrencia se descarta (registrada como `skipped: in flight`) mientras un handler de la función que inició antes del movimiento del reloj sigue ejecutándose, como hacía Cloud Scheduler en producción, y las ocurrencias de un mismo movimiento del reloj no cuentan unas contra otras.
- Una función cuenta como ocupada mientras cualquiera de sus ejecuciones esté en cola o en marcha, incluida una ejecución que espera para reintentarse, por lo que con `skip` y `reject` un reintento aún pendiente puede suprimir la siguiente ocurrencia; aquí Fireemu no distingue un intento de reintento de una ejecución solapada. Con `catchUp: all`, un movimiento del reloj sobre varias ocurrencias de la misma función se solapa consigo mismo, por lo que `skip` conserva la más antigua de ellas y `reject` cuenta el resto como rechazos.
- Si la cola de eventos de Functions está llena (4096 eventos activos o 64 MiB), una ejecución programada que vence sigue vencida y se ejecuta cuando se libera espacio.

### Ejecutar ahora una función programada

Una ejecución manual (`POST /v1/sessions/{session}/functions/{name}:run`) encola una ejecución de una función programada con la hora virtual actual. No consume la siguiente ocurrencia, que sigue venciendo y está sujeta a `scheduler.overlap` como cualquier ejecución. Este es un control propio de Fireemu, no una afirmación sobre el run-now de producción.

| Respuesta | Cuándo |
|---|---|
| `400 INVALID_ARGUMENT` | Una función desconocida, una función que no está programada, un rechazo de la política de solapamiento o un runtime que se está apagando |
| `429 RESOURCE_EXHAUSTED` | La cola de eventos está llena |

En una función de cola de tareas (`onTaskDispatched`), la misma ruta libera las Cloud Tasks que esperan su `scheduleTime`: todas, o la nombrada por un cuerpo `{"task": "<task id>"}` (404 cuando ninguna tarea en espera tiene ese id). Consulta [Colas de tareas](../../products/functions/#colas-de-tareas).

## Mover el reloj hacia atrás

El reloj puede moverse hacia atrás (`clock:set` con `"allowBackwards": true`, o **Allow moving backwards** en la página Runtime). Un retroceso nunca repite las ocurrencias que ya se ejecutaron.

### ID tokens tras un retroceso

- Con `strict`, Authentication (`INVALID_ID_TOKEN`), Firestore y Storage rechazan un ID token emitido después de la nueva hora hasta que el reloj vuelve a alcanzar su hora de emisión.
- En el perfil `emulator`, los ID tokens siguen siendo utilizables tras un retroceso, como con el emulador oficial, que no comprueba su hora de emisión.
- En ambos perfiles, un token caducado se sigue rechazando.

### Revocación tras un retroceso

Un retroceso a antes de que se creara una cuenta, o antes de que se revocaran sus tokens, hace que incluso el token de un inicio de sesión nuevo cuente como revocado. Vuelve a mover el reloj hacia delante o reinicia la sesión.

A la inversa, una revocación o un cambio de contraseña hecho tras un retroceso no revoca los tokens emitidos en momentos posteriores de la línea temporal: el perfil `emulator` los acepta de inmediato, y `strict` los acepta cuando el reloj alcanza su hora de emisión. Mueve el reloj hacia delante más allá de su hora de emisión antes de revocar, o reinicia la sesión.

## Horas que genera tu propio código

Algunas horas se generan fuera de fireemu, con el reloj real del equipo: el Admin SDK pone el `iat` y el `exp` de un token personalizado con `Date.now()`, `getSignedUrl()` firma una URL de Storage con la hora actual y `taskQueue().enqueue({scheduleDelaySeconds})` calcula el `scheduleTime` de la tarea a partir de `Date.now()`. Cuando el reloj del emulador está fijado o se ha movido (`daemon.clockStart`, `clock:advance`, todo mundo de `fireemu/testing`), no coincide con esas horas. `daemon.callerTimes` indica cómo se juzgan:

- `clockOrWall` (el valor predeterminado): un token personalizado o una URL firmada se aceptan cuando sus horas son válidas respecto al reloj del emulador o respecto a la hora real. Un `scheduleTime` más cercano a la hora real que al reloj de tareas conserva su retraso en el reloj de tareas, así que con `functions.clock.tasks = "virtual"` una tarea encolada con 60 segundos de retraso vence tras 60 segundos de tiempo del emulador (y al revés con un `Date` virtual y `tasks = "real"`). Es una suposición por el reloj más cercano: cuando los dos relojes están separados por menos del doble del retraso, la hora puede quedar más cerca del reloj de tareas y se toma tal cual, así que con el reloj de tareas 90 segundos por delante de la hora real esa tarea de 60 segundos vence de inmediato. Un rechazo indica el reloj del emulador y la hora real, por ejemplo `INVALID_CUSTOM_TOKEN : the token's iat and exp hold neither against the emulator clock (2026-01-01T00:00:00Z) nor against wall time (…)`.
- `clock`: cada una de esas horas se juzga solo con el reloj del emulador, como producción juzga con su único reloj, con los mensajes de producción. `productionExact` lo selecciona.

```json
{ "daemon": { "callerTimes": "clock" } }
```

## Con el reloj congelado

Un reloj detenido impide que llegue cualquier vencimiento hasta que lo muevas: los códigos de acción, los códigos SMS, los tokens de ID, el TTL de Firestore y las funciones programadas esperan a que se mueva el reloj. Hay dos diferencias:

- Las suscripciones pull de Pub/Sub guardan los plazos de confirmación y la espera de reintento en tiempo de entrega, que avanza con la hora real mientras el reloj está detenido. Un mensaje recibido y no confirmado vuelve tras su plazo de confirmación, y un nack con `retryPolicy` vuelve tras su espera, sin mover el reloj; adelantar el reloj sigue moviendo ambos. Las suscripciones push mantienen su espera en el reloj del emulador: adelántalo para liberar el siguiente intento. La primera vez que un endpoint push falla con el reloj detenido, el daemon muestra un aviso.
- La revocación compara segundos enteros, como en producción: `revokeRefreshTokens` o un cambio de contraseña en el mismo segundo que el inicio de sesión deja válido el token de ID de ese inicio de sesión. En producción una prueba espera un segundo antes de revocar; con el reloj congelado, adelanta el reloj al menos un segundo entre el inicio de sesión y la revocación. Con ese reloj, el daemon muestra un aviso cuando una revocación cae en el segundo del último inicio de sesión de la cuenta.

## Tiempo de aplicación en Functions

Por defecto, el código de tus funciones ve el tiempo real. Para que `Date.now()`, los temporizadores y Cloud Tasks sigan también el reloj virtual, establece `functions.clock`. Sin `daemon.clockStart`, el reloj empieza a la hora del reloj de pared y sigue el tiempo real, así que `Date.now()` en tus funciones lee la hora actual y los temporizadores virtuales se disparan tras su retraso a medida que pasa el tiempo real; un movimiento desplaza ambos. Fija también `daemon.clockStart` para una ejecución reproducible, en la que el reloj permanece quieto hasta que se mueve:

<Tabs syncKey="config-format">
<TabItem label="TOML">

```toml
# Configuration schema version: 1.
schemaVersion = 1

[daemon]
# Start the virtual clock at this date-time.
clockStart = "2026-01-31T23:59:00Z"

[functions]
# Directory of the Functions codebase.
source = "./functions"

[functions.clock]
# Functions date clock: "real" or "virtual".
date = "virtual"
# Functions timer clock: "real" or "virtual".
timers = "real"
# Cloud Tasks clock: "real" or "virtual".
tasks = "virtual"
```

</TabItem>
<TabItem label="JSON">

```json
{
  "schemaVersion": 1,
  "daemon": {
    "clockStart": "2026-01-31T23:59:00Z"
  },
  "functions": {
    "source": "./functions",
    "clock": {
      "date": "virtual",
      "timers": "real",
      "tasks": "virtual"
    }
  }
}
```

</TabItem>
</Tabs>

- Cada modo acepta `real` o `virtual`. Los temporizadores virtuales requieren `date` virtual.
- Con `tasks` establecido en `virtual`, una tarea de Cloud Tasks encolada con un `scheduleTime` vence cuando el reloj virtual lo alcanza, de modo que una prueba avanza el reloj en lugar de esperar.
- Con `tasks` establecido en `real`, la tarea espera al reloj de pared con `strict`. La página Functions de la [UI del emulador](../ui/) lista las tareas en espera y puede ejecutarlas ahora.
- Un codebase de Python ve siempre el tiempo real: no se mueve al reloj virtual, y una configuración que pide una fecha virtual para el runner de Functions se rechaza para él.
