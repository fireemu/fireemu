Fireemuは次の2種類の設定ファイルを読み込みます。

- **`fireemu.toml`**：[互換性プロファイル](../profiles/)、Authenticationのプロジェクト設定、仮想時計など、Fireemu固有の設定を記述します（`schemaVersion = 1`が必須）。JSON形式の`fireemu.json`も使えますが、同じディレクトリに両方を置くとエラーになります（[読み込まれるファイル](#読み込まれるファイル)）。全キーの一覧は[設定のスキーマ](../../reference/configuration/)を参照してください。
- **`firebase.json`**：既存のFirebase CLI用設定ファイルです。ポート、Security Rules、インデックス、Functionsコードベースを起動のたびに読み込みます。

## 両方のファイルを使う

Fireemu固有の設定は`firebase.json`に混ぜず`fireemu.toml`へ分け、`fireemu.toml`から`firebase.json`を参照させてください。

<Tabs syncKey="config-format">
<TabItem label="TOML">

```toml
#:schema https://raw.githubusercontent.com/fireemu/fireemu/v0.64.0/spec/config/fireemu.schema.json
# Configuration schema version: 1.
schemaVersion = 1
# Compatibility profile: "strict" or "emulator".
profile = "strict"
# Path to Firebase project configuration, relative to this file; a non-empty string.
firebaseJson = "firebase.json"
```

</TabItem>
<TabItem label="JSON">

```json
{
  "schemaVersion": 1,
  "profile": "strict",
  "firebaseJson": "firebase.json"
}
```

</TabItem>
</Tabs>

`npx fireemu init --firebase-json firebase.json`を実行すると、これが書き出されます。

## 読み込まれるファイル

`up`、`exec`、`emulators:start`、`emulators:exec`は次の優先順で設定ファイルを選びます。

1. **明示的なフラグ**：`--config <file>`や`--firebase-json <file>`を指定すると、自動探索を行わず指定ファイルだけを読み込みます。`--config`は拡張子が`.toml`（大文字小文字を区別しない）ならTOML、それ以外はJSONとして解釈します。TOML設定には`schemaVersion = 1`が必要で、JSON専用の`firebase.json`としては扱われません。`--firebase-json`は常にJSONとして読み込みます。
2. **カレントディレクトリのFireemu設定**：フラグ未指定の場合、カレントディレクトリにある`fireemu.toml`または`fireemu.json`を`--config`相当として読み込みます。
   - 両方のファイルが存在する場合は起動エラーになります。片方を削除するか、`--config`で明示してください。
   - `firebaseJson`キーは設定ファイルからの相対パスとして解決されます。`firebaseJson`の指定がない場合、同じディレクトリにある`firebase.json`は自動では読み込まれません（起動出力にもその旨が表示されます）。
   - 親ディレクトリにある`fireemu.toml`・`fireemu.json`は対象外です（記載パスがカレントディレクトリ基準のため）。
   - Fireemu設定内のファイルパス（`rules.source`、`storage.rules`、`functions.source`、`firestore.indexFile`など）は設定ファイルの場所にかかわらず作業ディレクトリ基準で解決されます。設定ファイル自身のディレクトリ基準になるのは`firebaseJson`と、`firebase.json`内に書かれたパスだけです。
3. **最も近い`firebase.json`**：カレントディレクトリにFireemu設定がなければ、Firebase CLIと同じくカレントディレクトリから親ディレクトリへ遡って最初に見つかった`firebase.json`を読み込みます。`firebase.json`内のパスと、その隣にある`.firebaserc`は、その`firebase.json`のディレクトリを基準に読み込まれます。
4. **組み込みの既定値**：いずれもなければ組み込みの既定値で起動し、Security Rulesは読み込まれません。

`--no-config-discovery`を付けると手順2と3の自動探索を無効にできます。実際に読み込まれたファイルは起動出力の`config:`行に表示されます。

自動探索が有効な場合、次の設定が反映されます。

- 見つかった`firebase.json`と同じディレクトリにある`.firebaserc`からプロジェクトIDを取得します。
- エミュレータのポート、Hub、UI、単一プロジェクト設定が適用されます。
- `functions`エントリがあればFunctionsランタイムも起動します。
- `fireemu capabilities`でも、見つかった`fireemu.toml`のプロファイルが反映されます。

テストと同じディレクトリにある`firebase.json`を無視していた以前の挙動が必要な場合は、`--no-config-discovery`を指定してください。

## 相対パス

相対パスは、書かれているファイルによって、異なるディレクトリを基準に解決されます。

| パスが書かれている場所 | 解決の基準 |
|---|---|
| `fireemu.toml`または`fireemu.json`: `rules.source`、`firestore.indexFile`、`storage.rules`、`functions.source`など、ファイルを指す設定 | `fireemu`を実行する作業ディレクトリ |
| `--functions <dir>`とその他のパスオプション | 作業ディレクトリ |
| `fireemu.toml`または`fireemu.json`の`firebaseJson` | その設定ファイルのディレクトリ |
| `firebase.json`内のすべてのパス(`firestore.rules`、`functions.source`、`hosting.public`など) | その`firebase.json`のディレクトリ |

そのため、リポジトリのルートから実行した`fireemu exec --config packages/api/fireemu.toml -- npm test`は、`rules.source = "firestore.rules"`を`packages/api`ではなくリポジトリのルートから読み取ります。Fireemuは互換性のためにこの動作を維持しています。将来のスキーマバージョンでは、すべてのパスが設定ファイルを基準に解決されるようになる可能性があります。

この違いを避けるには、設定があるディレクトリからFireemuを実行するか、`firebaseJson`が参照する`firebase.json`にパスを書いてください。

[`fireemu up --plan`](../../reference/cli/#実行を計画する)は、すべてのパスについて、実行が開く絶対パスと、解決の基準になったディレクトリを表示します。正規設定のパスが、設定ファイル自身のディレクトリからの解決と異なる結果になる場合は、警告を表示します。

## ファイル所有者のチェック

探索されたファイルは、実行するFunctionsのコードや適用するルールを指定できます。そのためUnixでは、gitがリポジトリの所有者を確認するのと同様に、探索で見つかったものの所有者を検索時に確認します。Firebase CLIはこれを確認しません。Windowsでは所有者は確認されません。

信頼される所有者は、あなた自身、root、そして`sudo`でrootとして実行している場合は`SUDO_UID`のユーザーです。

- **設定ファイル。** 所有者が信頼されていない、または任意のユーザーが書き込める`fireemu.toml`、`fireemu.json`、`firebase.json`は、警告を出してスキップされます。グループ書き込みは許可されているため、ユーザープライベートグループのumask(002、DebianとUbuntuのデフォルト)で作成されたファイルは読み込まれます。
- **`.firebaserc`。** プロジェクトとターゲットのエイリアスのみを指定し、コードやルールは指定しないため、所有者は確認されません。それ自身またはそのディレクトリに任意のユーザーが書き込める場合にのみ、スキップされます。
- **親ディレクトリ。** 検索は、所有者が信頼されていない、または任意のユーザーが書き込める親ディレクトリ(`/tmp`など)の手前で止まります。また、入る権限がないなど、検査できない親ディレクトリでも、警告なしで止まります。
- **カレントディレクトリ。** そこで実行すると選んだのはあなたなので、所有者は確認されません。任意のユーザーが書き込めるカレントディレクトリは、まったく検索されません。
- **シンボリックリンク。** シンボリックリンクは、それが指すファイルで判定されます。ターゲットを保持するディレクトリは確認されません。
- **読み取り。** 各候補は一度だけ開かれます。何かを読む前に、開いたファイルで所有者とモードが確認され、そのテキストは同じファイルから読み取られます。16 MiBを超える探索済みファイルは、エラーで拒否されます。

スキップされたファイルやディレクトリは警告に名前が示され、何も見つからなかったかのように実行が続きます。探索されたファイルのエラーには、検索でそのファイルが見つかったことが示されます。

- スキップされたファイルをそれでも読み込むには、`--config`または`--firebase-json`で名前を指定します。
- 警告を抑えるには、`--no-config-discovery`を渡します。

この規則に当たりやすい設定が2つあります。

- **バインドマウントされたチェックアウトを持つrootコンテナ。** GitHub Actionsの`container:`ジョブや、rootでの`docker run -v "$PWD":/app`などです。ファイルは、コンテナのrootが信頼しないホストユーザーが所有しています。明示的なフラグを使うか、チェックアウトを`chown`してください。`.firebaserc`は引き続きプロジェクトを指定します。ルートレスのPodmanは、あなたのユーザーをコンテナのrootにマップするので、影響を受けません。
- **`sudo`。** `SUDO_UID`のユーザーが所有するファイルは信頼されます。

## 設定を検証する

`fireemu.toml`は起動時に検証されます。Fireemuが受け付けない値があると、エラーで停止します。

- `up`、`exec`、`config show`は、どちらの形式でも、スキーマに載っていないキーと型の誤った値を拒否します。エラーには、ファイル、キー、本来あるべき型が示されます。たとえば`fireemu.toml: daemon.firestorePort must be an integer, found a string`のようになります。
- 整数の設定は、値が整数であっても浮動小数点数を拒否します。エラーメッセージが示すように、`8080.0`ではなく`8080`と書いてください。
- [設定スキーマ](../../reference/configuration/)はJSON Schemaで、エディタでも使えます。

設定が何に解決されるかを表示するコマンドが2つあります。

- `fireemu capabilities`は、設定が解決するプロファイルのケイパビリティマニフェストを表示します。
- `fireemu up --plan`と`fireemu exec --plan -- <command>`は、ファイル、コマンドライン、環境から実行が解決するすべて(プロジェクト、サービス、ポート、ファイル、Functionsランタイム、継承された変数)を、実行を開始せずに表示します。[実行を計画する](../../reference/cli/#実行を計画する)を参照してください。

## リファレンスファイルを生成する

`fireemu init --reference`は、スキーマから生成されるコメント付きのリファレンスである`fireemu.reference.toml`も書き出します。既存の`fireemu.json`がある場合は、代わりに`fireemu.reference.jsonc`を書き出すため、リファレンスのキーは設定の形式に合います。Fireemuはこのファイルを読み込みません。

- 通常の`fireemu.toml`は最小限のままです。リファレンスのキーをコピーするとそのキーが明示的になり、`productionExact`が切り替えなくなります。
- リファレンスでは、次のキーはコメントアウトされたままです。デフォルトのないキー、存在すること自体が動作を選択するキー、`productionExact`が制御するキー、将来の互換性のために受け付けられるが現在は効果がないキー(コメントにその旨が記されています)。
- `fireemu config lint --deny-ineffective`は、設定が、受け付けられるが効果のないキーを設定している場合に、CIジョブを失敗させます。`--allow`と`--allow-file`で、意図的に残すものを列挙します([`config lint`](../../reference/cli/#config-lint)を参照)。
- 初期化するときは、`--reference`を`--profile`や`--firebase-json`と組み合わせてください。既存の`fireemu.toml`または`fireemu.json`があり、それらのオプションのどちらもない場合は、リファレンスだけが書き出されます。
- 既存の出力ファイルを置き換えるには`--force`が必要です。

### スキーマの注釈

リリース版のバイナリでは、生成されるスキーマの注釈は、GitHubリポジトリにあるそのリリースのスキーマファイル(`https://raw.githubusercontent.com/fireemu/fireemu/v<version>/spec/config/fireemu.schema.json`)を参照するため、エディタは、インストールされたバージョンが受け付けるキーに対してファイルを検査します。ソースからビルドしたバイナリ(リリース間のビルドを含み、そのバージョンのタグより新しいスキーマを埋め込んでいます)は、代わりに`main`の場所を書き出します。

任意のリリースタグ、`main`、または古い`https://fireemu.dev/spec/config/fireemu.schema.json`の場所を指す`$schema`または`#:schema`も、引き続き読み込まれます。エディタでの検証のために、古い注釈は、実行しているバージョンのタグに置き換えてください。

Fireemuは同梱のスキーマに対して検証し、注釈のURLを取得しません。`fireemu config schema --out <path>`は、GitHubに接続できないエディタやツールのために、その同梱スキーマをファイルに書き出します。

## TOMLの値とJSONのnull

TOMLファイルは、JSONファイルと同じJSON Schema、検証、デフォルトを使います。

- ファイルの先頭を`#:schema https://raw.githubusercontent.com/fireemu/fireemu/v0.64.0/spec/config/fireemu.schema.json`(`v0.64.0`は例です。実行しているバージョンのタグを使ってください)で始めると、TaploまたはEven Better TOMLでスキーマが選択されます。
- タイムスタンプの値は引用符で囲んでください。スキーマにdatetime型がないため、TOMLのdatetimeはキー名とともに拒否されます。

TOMLには`null`がありません。以下のnull許容の設定すべてで、そのキーを含むテーブルでキーを省略してください。null許容の配列要素では、その要素を省略します。存在自体に意味がある場合は、含むテーブルや配列は残してください。空の配列と空のテーブルは、既存の意味を保ちます。

| null許容のJSONキー | nullとTOMLでの省略の意味 |
|---|---|
| `limits.queryCatalog`、`firestore.textSearch.visibilityLag` | 受け付けられるが、実行時の効果はない。省略すると、これらのキーの明示的な値と起動時の注記も削除される。 |
| `limits.firestorePlan.compositeIndexLimitOverride`、`limits.firestorePlan.singleFieldConfigLimitOverride`、`limits.firestorePlan.enterpriseIndexLimitOverride` | オーバーライドなし。nullでないオーバーライドは現在拒否される。 |
| `auth.providers`、`auth.providers.oidc`、`auth.providers.saml` | プロバイダーのシード宣言なし。空の配列は空の置き換えを明示的に宣言するもので、省略とは異なる。 |
| `auth.providers.oidc[].displayName`、`auth.providers.oidc[].clientSecret`、`auth.providers.saml[].displayName` | 任意のプロバイダー値なし。 |
| `auth.authorizedDomains` | シードなし。デフォルトのドメインを維持する。空の配列はドメインなしを宣言する。 |
| `auth.authorizedDomains[]` | この要素を無視する。TOMLの配列から除外する。 |
| `auth.mfa`、`auth.multiTenant`、`auth.tenants` | 宣言なし。該当するデフォルトを維持する。 |
| `auth.mfa.enabledProviders`、`auth.mfa.providerConfigs` | 宣言されたMFA設定に、この種類のプロバイダーはない。MFAを宣言する場合は`auth.mfa`テーブルを維持する。 |
| `auth.mfa.providerConfigs[].totpProviderConfig` | このプロバイダーエントリを無視する。そのエントリでキーを省略する。 |
| `auth.mfa.providerConfigs[].totpProviderConfig.adjacentIntervals` | 宣言されたTOTPプロバイダーで、隣接する間隔をゼロにする。そのテーブルは維持する。 |
| `auth.blockingFunctions.triggers.beforeCreate`、`auth.blockingFunctions.triggers.beforeSignIn` | 明示的なトリガー選択で、このトリガーを無効にする。`[auth.blockingFunctions.triggers]`は維持する。そのテーブル全体を省略すると、代わりにディスカバリーが有効になる。 |
| `auth.quota.signUpQuotaConfig` | インポートされたオーバーライドを含め、一時的なクォータのオーバーライドを解除する。`[auth.quota]`は空のまま維持する。クォータのテーブル全体を省略すると、インポートされたオーバーライドが維持される。 |
| `auth.passwordPolicy.constraints.maxLength`、`auth.passwordPolicyOverrides[].passwordPolicy.constraints.maxLength` | カスタムの最大長なし。 |
