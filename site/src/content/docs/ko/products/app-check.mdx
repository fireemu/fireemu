Fireemu에는 로컬 App Check 구현이 포함되어 있습니다. 디버그 토큰 교환, JWKS, 그리고 Authentication, Firestore, Storage, callable 함수에 대한 검증을 제공합니다. Local Emulator Suite에는 App Check 에뮬레이터가 없습니다.

## 테스트할 수 있는 항목

- `strict`에서 별도 설정 없이 동작하는 디버그 토큰 교환([설정 없이 디버그 토큰 교환](#설정-없이-디버그-토큰-교환)).
- Authentication, Firestore, Storage에 대한 적용: `off`, `unenforced`, `enforced`([앱 등록과 적용](#앱-등록과-적용)).
- `request.app`을 포함해 `enforceAppCheck`를 사용하는 callable 함수([Callable 함수](#callable-함수)).
- 없거나, 형식이 잘못되었거나, 만료되었거나, 서명이 잘못된 토큰의 거부.
- `onRequest` 함수 안의 `getAppCheck().verifyToken()`([Admin SDK로 검증](#admin-sdk로-검증-getappcheckverifytoken)).

## 연결

교환 엔드포인트는 `POST /v1/projects/{project}/apps/{appId}:exchangeDebugToken`입니다. 호스트는 `FIREEMU_APP_CHECK_EMULATOR_HOST`입니다. `fireemu exec`가 명령에 이 값을 설정해 주고, `fireemu up`은 시작 출력에 이 값을 출력합니다. 이는 제어 리스너의 주소이며, Authentication이 선택되어 있으면 Authentication 포트(기본값 9099)입니다.

### 설정 없이 디버그 토큰 교환

`strict` 프로필에서는 디버그 토큰 교환, JWKS, callable 신뢰 경계가 `appCheck` 블록 없이도 제공되며, 모든 제품의 기준값은 `off`입니다.

- 올바른 형식의 디버그 토큰(UUIDv4)은 표준 앱 ID(`1:<project number>:<platform>:<id>`)를 가진 어떤 앱에 대해서도 토큰으로 교환됩니다. 앱은 처음 사용할 때 등록됩니다.
- 따라서 `enforceAppCheck` callable은 앱 등록이나 해시 없이 교환으로 받은 토큰으로 테스트할 수 있으며, 토큰이 없거나 형식이 잘못된 경우는 여전히 거부됩니다.
- 키 쌍은 시작 후 백그라운드에서 생성되므로 첫 교환이 이를 기다리지 않습니다.

예를 들어 `fireemu up`이 실행 중이고 `appCheck` 블록이 없으면 어떤 UUIDv4든 교환됩니다(호스트는 `FIREEMU_APP_CHECK_EMULATOR_HOST`로 출력된 값입니다).

```sh
curl -X POST 'http://127.0.0.1:9099/v1/projects/demo-app/apps/1%3A1234567890%3Aweb%3Alocal-test-app:exchangeDebugToken' \
  -H 'content-type: application/json' \
  -d "{\"debugToken\":\"$(uuidgen | tr 'A-F' 'a-f')\",\"limitedUse\":false}"
# {"token":"eyJhbGciOiJSUzI1NiIs...", "ttl": "..."}
```

UUIDv4가 아닌 문자열은 `403 PERMISSION_DENIED`, `App attestation failed.`로 거부됩니다.

`appCheck.debugTokens`가 이를 제어합니다. `appCheck.enabled: true`와 함께 직접 `"any"`로 설정하면, 등록한 앱에 대해서도 해시가 무엇이든 어떤 UUIDv4든 교환됩니다. 이 경우에는 `"any"`이고, `productionExact`에서, `emulator` 프로필에서, 그리고 이 키를 설정하지 않은 `appCheck` 블록에서는 프로덕션의 규칙인 `"registered"`입니다. `"registered"`에서는 [App Check를 활성화](#앱-등록과-적용)하기 전에는 아무것도 제공되지 않습니다.

따라서 `appCheck.enabled`만으로는 App Check가 제공되는지 알 수 없습니다. 이 기본값에서는 교환과 callable 적용이 켜져 있어도 `false`로 남습니다. `fireemu config show`는 키 바로 아래에 실제로 적용되는 내용을 시작 배너와 같은 용어로 출력합니다.

```text
appCheck.enabled = false (default)
  in effect: auth = off; callables = on: enforceAppCheck is honoured per function; exchange = on: any well-formed debug token (appCheck.debugTokens "any"); firestore = off; storage = off
```

`config show --json`은 같은 상태를 `appCheck.enabled` 행의 `effective` 객체로 담습니다.

### Web SDK에서 토큰 받기

`@firebase/app-check`는 항상 프로덕션 교환 엔드포인트를 호출하므로, 디버그 토큰을 Fireemu와 교환하는 `CustomProvider`를 사용하십시오. 브라우저 번들은 `process.env`를 읽을 수 없으므로, 번들러 자체의 설정을 통해 호스트를 전달하십시오.

<Tabs syncKey="code-language">
<TabItem label="TypeScript">

```ts
import { initializeApp } from 'firebase/app';
import {
  CustomProvider,
  getToken,
  initializeAppCheck,
  type AppCheckTokenResult,
} from 'firebase/app-check';

const APP_ID = '1:1234567890:web:local-test-app';
const host = process.env.FIREEMU_APP_CHECK_EMULATOR_HOST;
const debugToken = process.env.DEBUG_TOKEN;
if (!host || !debugToken) throw new Error('Set FIREEMU_APP_CHECK_EMULATOR_HOST and DEBUG_TOKEN');

async function exchangeDebugToken(): Promise<AppCheckTokenResult> {
  const url = `http://${host}/v1/projects/demo-app/apps/${encodeURIComponent(APP_ID)}:exchangeDebugToken`;
  const response = await fetch(url, {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({ debugToken, limitedUse: false }),
  });
  if (!response.ok) throw new Error(`exchange refused: ${response.status}`);
  const body = (await response.json()) as { token: string; ttl: string };
  const ttlSeconds = Number.parseInt(body.ttl.replace(/s$/, ''), 10);
  return { token: body.token, expireTimeMillis: Date.now() + ttlSeconds * 1000 };
}

const app = initializeApp({ projectId: 'demo-app', apiKey: 'fake-api-key', appId: APP_ID });
const appCheck = initializeAppCheck(app, {
  provider: new CustomProvider({ getToken: exchangeDebugToken }),
});

const { token } = await getToken(appCheck);
```

변수를 설정하고 실행합니다. `fireemu exec` 아래에서는 `DEBUG_TOKEN`만 직접 설정하면 됩니다.

```sh
export DEBUG_TOKEN=$(uuidgen | tr 'A-F' 'a-f')

# fireemu exec sets FIREEMU_APP_CHECK_EMULATOR_HOST for the command

# with fireemu up running, copy the host from its startup output
```

TypeScript 버전은 로컬 `fireemu up` 0.48.0, `firebase` 12.18.0, Node.js 24(type stripping)에서 실행했으며 `getToken`이 토큰을 반환했습니다. `appCheck` 블록이 없으면 어떤 UUIDv4든 교환됩니다. 앱이 등록되어 있으면 토큰의 해시가 앱의 `debugTokenSha256` 값 중 하나여야 합니다.

## 설정

### 앱 등록과 적용

Authentication, Firestore, Storage에 App Check를 적용하거나 등록을 요구하려면, 이를 활성화하고 앱을 디버그 토큰의 SHA-256 해시와 함께 등록하십시오. 설정에는 해시만 저장되며 원본 토큰은 절대 저장되지 않습니다.

각 서비스는 `off`, `unenforced`(토큰을 검사하고 기록하지만 요청은 통과), `enforced`(유효한 토큰이 없는 요청은 Security Rules가 실행되기 전에 거부)를 받습니다. 등록된 앱이 없는 프로젝트는 App Check를 사용할 수 없으므로, 적용 중인 서비스는 해당 서비스에 대한 모든 요청을 거부합니다.

`--only`는 설정된 기준값이 필요로 하는 검증기를 유지합니다. `appCheck.services.firestore = "enforced"`이면 `--only firestore`에서도 유효한 토큰이 없는 요청은 여전히 거부되며, 시작 배너에 검증기가 포함되었다고 표시됩니다.

### 디버그 토큰과 해시 생성

디버그 토큰은 UUIDv4이며, 해시는 소문자 형태에 대해 계산합니다. 테스트용 토큰을 생성하고 그 해시를 계산합니다.

```sh
DEBUG_TOKEN=$(uuidgen | tr 'A-F' 'a-f')
printf %s "$DEBUG_TOKEN" | shasum -a 256 | cut -d' ' -f1
```

그 밖의 문자열은 일치하지 않으며, 교환은 403으로 응답합니다.

### 서버 측 코드의 Storage 요청

Storage가 `enforced`일 때도, Admin SDK나 `gcloud`(브라우저가 아닌 클라이언트 라이브러리)를 사용하는 서버 측 코드는 토큰 없이 Storage에 접근할 수 있어야 합니다. 프로덕션은 이 트래픽에 App Check를 적용하지 않습니다. Admin SDK는 OAuth를 통해 서비스 계정으로 인증하며, 적용 대상은 클라이언트 SDK가 호출하는 Firebase Storage API입니다. 에뮬레이터에는 OAuth가 없으므로 `appCheck.storageServerRequests`가 이 트래픽을 어떻게 인식할지 결정합니다.

| | `"loopback"` (기본값) | `"capability"` |
|---|---|---|
| 토큰 없이 허용되는 요청 | 루프백 피어에서 루프백 `Host`로 오는, 브라우저 증거가 없고 클라이언트 SDK 자격 증명이 없는 Cloud Storage JSON API 요청([세부 사항](#how-loopback-recognises-a-request)) | `fireemu exec`가 `STORAGE_EMULATOR_HOST`의 userinfo(`http://fireemu:<capability>@host:port`)에 넣어 주는 실행별 capability를 가진 요청만 |
| `STORAGE_EMULATOR_HOST` | 일반적인 `http://host:port`이며, 모든 `@google-cloud/storage`와 `firebase-admin` 버전이 받아들입니다 | capability가 포함됩니다. `@google-cloud/storage` 8.1 이상(`firebase-admin` 14.4 이상)은 자격 증명이 포함된 URL을 거부합니다 |
| `file.save()`와 재개 가능한 업로드 | 동작함: 재개 가능한 업로드의 이어 보내기도 이런 요청입니다 | 해당 버전이나 재개 가능한 업로드를 쓰면 Admin SDK가 적용 중에 실패함: 이어 보내기 URL에는 capability가 없습니다 |
| 브라우저가 아닌 로컬 프로세스(`curl`, 테스트 스크립트) | 토큰 없이 통과 | capability가 없으면 거부 |
| `enforced` Storage 서비스가 증명하는 것 | 로컬 클라이언트가 토큰을 제시했다는 것은 아님 | capability가 아닌 것은 아무것도 통과하지 못했다는 것 |
| 루프백이 아닌 호스트 이름(`host.containers.internal`, LAN 주소에 게시된 포트)으로 에뮬레이터에 접근하는 컨테이너 | 인식되지 않음: 토큰 또는 `"capability"`가 필요 | capability가 필요 |
| `fireemu` 아래에서 실행하는 Cloud Function 안의 Admin SDK | 통과: 같은 일반 `STORAGE_EMULATOR_HOST`를 받습니다(프로덕션에서는 App Check가 검사하지 않는 함수의 서비스 계정을 사용합니다) | 통과하지 못함 |

Firebase Storage API(`/v0`, `firebase/storage`와 모바일 SDK가 사용하는 것)는 항상 토큰이 필요하며, 페이지나 다른 호스트에서 온 것처럼 보이는 요청도 마찬가지입니다. 이는 프로덕션의 동작이므로 emulator와 strict 프로필, 그리고 `productionExact`에서 모두 같습니다. Storage 적용이 없으면 `STORAGE_EMULATOR_HOST`는 항상 일반적인 `http://host:port`입니다.

<details id="how-loopback-recognises-a-request">
<summary><code>"loopback"</code>이 요청을 인식하는 방법</summary>

`"loopback"`은 Cloud Storage JSON API 경로(`/storage/v1`, `/upload/storage/v1`, `/download/storage/v1`)의 요청 중 다음 조건을 모두 만족하는 요청을 허용합니다.

- 루프백 피어에서 옵니다.
- 루프백 `Host`(`localhost` 또는 `127.0.0.1`, `[::1]` 같은 루프백 IP 주소)를 향합니다. `evil.example` 같은 리바인딩된 DNS 이름은 해당하지 않습니다.
- 브라우저 증거가 없습니다. 비어 있지 않은 값을 가진 `Origin`, `Sec-Fetch-Site`, `Sec-Fetch-Dest`, `Referer`, `Cookie` 헤더가 없어야 합니다(빈 값은 없는 것으로 간주합니다).
- 클라이언트 SDK의 `Authorization: Firebase <token>` 자격 증명을 제시하지 않습니다.

Admin SDK가 버킷 메타데이터에 사용하는 짧은 `/b/{bucket}` 표기도 JSON API 경로로 간주합니다. 재개 가능한 업로드의 이어 보내기도 이런 요청이므로 `file.save()`가 동작합니다. `fireemu exec`는 일반적인 `STORAGE_EMULATOR_HOST=http://host:port`를 내보냅니다.

</details>

capability를 가진 요청만 허용하려면 다음과 같이 합니다.

## Callable 함수

Node callable의 `enforceAppCheck: true`는 유효한 토큰이 없는 호출을 함수가 실행되기 전에 callable `UNAUTHENTICATED` 오류로 거부합니다(401 응답, 또는 스트리밍 호출의 경우 `200` SSE 오류 레코드). 유효한 토큰은 `request.app`을 채웁니다.

재사용 방지(replay protection)는 지원되지 않습니다. `consumeAppCheckToken: true`인 callable에 유효한 토큰을 제시한 호출은 501 `APP_CHECK_REPLAY_UNSUPPORTED`로 거부되므로, 프로덕션이라면 소비했을 토큰으로 테스트가 통과하는 일은 없습니다.

토큰은 하나의 데몬 인스턴스에 속한 키로 서명됩니다. Node callable과 데몬이 검증하는 다른 서비스는 세션 리셋이나 스냅샷 복원 이후에 이 토큰을 거부합니다.

Python callable은 현재 앱 상태나 프로젝트 epoch를 확인하지 않고, 서명 키와 실제 시간을 사용해 토큰 서명과 클레임을 검증하므로, 프로젝트를 리셋하거나 앱을 비활성화해도 그 밖에는 유효한 토큰이 만료 전에 폐기되지 않습니다. Python은 토큰 소비와 명시적인 App Check 설정도 거부합니다. 설정과 제한은 [Cloud Functions (Python)](../functions-python/#프로덕션-및-firebase-cli와의-차이)을 참고하십시오.

## 일반 HTTP 함수(`onRequest`)

callable과 달리 `onRequest` 핸들러는 자동 검증이나 `request.app` 없이 `X-Firebase-AppCheck` 헤더를 받습니다. 핸들러가 직접 검증하고 검증된 앱이 무엇을 할 수 있는지 결정해야 합니다. callable의 `enforceAppCheck`는 별도의 HTTP 엔드포인트를 보호하지 않습니다.

### Admin SDK로 검증 (`getAppCheck().verifyToken()`)

배포하는 코드는 그대로 동작합니다. `onRequest` 함수 안의 `getAppCheck().verifyToken(token)`은 Google의 키가 아니라 데몬이 응답합니다.

```js
import { onRequest } from 'firebase-functions/v2/https';
import { initializeApp } from 'firebase-admin/app';
import { getAppCheck } from 'firebase-admin/app-check';

initializeApp();

export const api = onRequest(async (req, res) => {
  try {
    const { appId } = await getAppCheck().verifyToken(req.get('X-Firebase-AppCheck'));
    // application logic for a verified app
  } catch {
    res.status(401).send('Unauthorized');
  }
});
```

러너는 코드가 로드되기 전에 코드베이스에서 해석되는 `firebase-admin`을 패치합니다. SDK는 여전히 토큰을 디코딩하고 알고리즘, audience, issuer, subject를 스스로 검사하며, 서명 단계만 러너의 비공개 파이프를 통해 데몬에 묻는 것으로 대체됩니다. 데몬은 callable 함수에 사용하는 것과 같은 검증기로, 현재 프로젝트 epoch와 앱 레지스트리를 기준으로, 가상 시계에서 응답하며 아무것도 캐시하지 않습니다. 따라서 제자리 세션 리셋이나 스냅샷 복원 이전에 발급된 토큰은 데몬이 더 이상 키를 가지고 있지 않은 토큰과 똑같이 거부됩니다(`app-check/invalid-argument`, "... does not correspond to a known public key ..."). 오류는 SDK 자체의 오류 매퍼가 만든 SDK 고유의 오류입니다.

- 지원: Functions 코드베이스에서 해석되는 `firebase-admin` 13 및 14. 14.3.0(CI)과 13.10.0에서 테스트했습니다. 14.5.0은 App Check 코드가 14.3.0과 동일하므로(`token-verifier.js`, `app-check.js`, `app-check-api-client-internal.js`, `utils/jwt.js` 파일은 버전 배너만 다릅니다) CI에 설치하지 않으며, 이 파일들의 내용을 고정하는 테스트가 있어 이를 바꾸는 의존성 업데이트는 CI에서 실패합니다. 이 범위 밖이거나 SDK 내부가 바뀌어 시작 시 자체 테스트가 실패하면 아무것도 패치하지 않고 데몬이 시작 시 안내를 출력하며, `verifyToken`은 Fireemu 토큰을 거부합니다(확인할 수 없는 토큰은 절대 받아들이지 않습니다). `node_modules`의 다른 위치에 있는 두 번째 `firebase-admin` 사본은 러너가 해석하는 것이 아니므로 기본 상태로 남습니다.
- `verifyToken(token, { consume: true })`은 토큰이 검증된 뒤 `app-check/unimplemented`로 거부됩니다. 제한된 사용(limited-use) 소비는 구현되지 않았으며, 프로덕션 App Check API는 절대 호출되지 않습니다. `getAppCheck().createToken()`은 다른 호출이며 여전히 Google의 교환 엔드포인트로 갑니다.
- 데몬은 Functions 러너가 속한 프로젝트에 대해 검증합니다. 다른 프로젝트 ID를 지목하는 앱의 호출은 알 수 없는 키로 응답됩니다.
- 프로덕션과의 차이: 프로덕션은 등록되지 않았거나 비활성화된 앱의 토큰을 만료될 때까지 받아들입니다. Fireemu는 모든 프로필에서 이를 거부합니다. `iat`가 미래인 토큰은 프로덕션과 마찬가지로 검증됩니다.
- 여기 있는 어떤 것도 `onRequest`가 자동으로 검증하게 만들지 않습니다. 검증된 앱이 무엇을 할 수 있는지는 여전히 핸들러가 결정하며, App Check는 사용자가 아니라 앱을 식별합니다.

### 각 프로세스에서의 엔드포인트 탐색

| 프로세스 | 사용 가능한 라우팅 |
| --- | --- |
| `fireemu exec` 자식 프로세스 또는 `world.environment` | App Check를 사용할 수 있을 때 `FIREEMU_APP_CHECK_EMULATOR_HOST`와 `FIREEMU_APP_CHECK_JWKS_URL`. JWKS URL은 `http://host:port/v1/jwks`입니다. |
| 번들된 Functions 러너 | App Check를 사용할 수 있을 때, Auth가 선택되지 않았더라도 `FUNCTIONS_EMULATOR=true`와 같은 App Check 호스트/JWKS 변수. 상속된 값, dotenv, 로컬 시크릿 값은 이 두 경로를 대체할 수 없으며, App Check를 사용할 수 없으면 제거됩니다. |
| 부모 테스트 프로세스 | world 변수는 `process.env`에 설치되지 않습니다. `world.environment`를 명시적으로 사용하십시오. |

러너 안에서는 `FIREEMU_APP_CHECK_JWKS_URL`을 사용하십시오. 요청 헤더나 검증되지 않은 토큰에서 키 URL을 도출하지 마십시오.

### Admin SDK 없이 로컬에서 서명과 클레임 검증

미들웨어가 Admin SDK 대신 JWKS 라이브러리로 검증한다면 Functions 패키지에 `jose`를 설치하십시오. 아래의 프로젝트 번호, 프로젝트 ID, 허용 앱 ID는 테스트 설정에서 가져와야 합니다. 허용 앱 집합은 이 엔드포인트가 허용하려는 활성 앱을 반영해야 합니다. 이 예제는 의도적으로 루프백만 지원합니다.

```js
import { createRemoteJWKSet, jwtVerify } from 'jose';
import { getAppCheck } from 'firebase-admin/app-check';

const projectId = 'demo-app';
const projectNumber = '1234567890';
const allowedApps = new Set(['1:1234567890:web:local-test-app']);
let localKeys;

export async function verifyHttpAppCheck(token) {
  if (process.env.FUNCTIONS_EMULATOR !== 'true') {
    return getAppCheck().verifyToken(token);
  }
  if (!localKeys) {
    const address = process.env.FIREEMU_APP_CHECK_JWKS_URL;
    if (!address) throw new Error('Local App Check is unavailable');
    const url = new URL(address);
    if (url.protocol !== 'http:' || !['127.0.0.1', '[::1]'].includes(url.hostname) || !url.port ||
        url.username || url.password || url.pathname !== '/v1/jwks' || url.search || url.hash) {
      throw new Error('Expected the loopback App Check JWKS URL');
    }
    localKeys = createRemoteJWKSet(url);
  }
  const now = new Date();
  const { payload, protectedHeader } = await jwtVerify(token, localKeys, {
    algorithms: ['RS256'],
    issuer: `https://firebaseappcheck.googleapis.com/${projectNumber}`,
    requiredClaims: ['sub', 'aud', 'iat', 'exp', 'jti'],
    currentDate: now,
    clockTolerance: 0,
  });
  const audiences = [`projects/${projectNumber}`, `projects/${projectId}`];
  if (protectedHeader.typ !== 'JWT' ||
      typeof protectedHeader.kid !== 'string' || !protectedHeader.kid ||
      !Array.isArray(payload.aud) || !audiences.every(a => payload.aud.includes(a)) ||
      !allowedApps.has(payload.sub) ||
      !Number.isInteger(payload.iat) || !Number.isInteger(payload.exp) ||
      payload.iat > Math.floor(now.getTime() / 1000) || payload.exp <= payload.iat ||
      typeof payload.jti !== 'string' || !payload.jti) {
    throw new Error('Invalid local App Check token');
  }
  return { ...payload, app_id: payload.sub };
}
```

`onRequest` 핸들러에서 `req.get('X-Firebase-AppCheck')`와 함께 이를 호출하십시오. 헤더가 없거나 검증에 실패하면 애플리케이션 로직을 실행하기 전에 일반적인 401로 거부하십시오. 검증 세부 정보를 반환하거나 토큰을 로그에 남기지 마십시오. App Check는 사용자가 아니라 앱을 식별하므로, Auth와 멤버십 검사도 함께 유지하십시오.

예제의 `new Date()`는 토큰 교환과 같은 시계를 사용해야 합니다. 테스트 world는 Functions에서 기본적으로 가상 Date를 사용하며, 고정된 시계를 쓰는 일반 데몬은 `functions.clock.date = "virtual"`도 필요합니다. 부모 테스트 프로세스와 `world.run` 자식 프로세스는 네이티브 Date를 유지하므로, 이 검증기를 거기에 복사하려면 world 시간을 명시적으로 제공해야 합니다.

**이는 서명과 클레임 검증이며 Fireemu의 전체 검증기가 아닙니다.** JWKS는 현재 프로젝트 epoch나 앱 레지스트리를 노출하지 않지만, 위의 Admin SDK 경로는 노출합니다. 이 예제는 같은 서명 키를 계속 사용할 수 있는 동안 제자리 세션 리셋, 스냅샷 복원, 프로젝트 삭제, 앱 비활성화 이후에 이전에 발급된 토큰을 거부할 수 없습니다. `fireemu_epoch`가 존재하는지만 확인해서는 이를 해결할 수 없습니다. 토큰 소비나 재사용 방지도 구현하지 않습니다.

이 레시피를 사용하는 테스트에서는 Functions 러너를 포함해 전체 world를 `world.reset()`으로 다시 만들거나(또는 폐기하고 다른 world를 만들어) 새 토큰을 받으십시오. 그러면 데몬 키와 검증기 캐시가 교체됩니다. 이 우회 방법을 데몬의 epoch 무효화 동작에 대한 증거로 취급하지 마십시오. 그 동작을 테스트하려면 callable 검증 경계를 사용하십시오.

## Firestore WebChannel 거부

Firestore WebChannel의 App Check 거부는 HTTP 403인 REST 거부와 달리, HTTP 200 전송 협상 이후 종료형 `PERMISSION_DENIED` 프로토콜 오류로 도착합니다. 기존 채널의 잘못되었거나 다른 앱의 교체 토큰은 보존된 문서를 재생할 수 없습니다. [Listen 스트림](../firestore/#listen-스트림)을 참고하십시오.

## 프로덕션과의 차이

다음은 의도적으로 범위에서 제외한 항목입니다.

- **Play Integrity, App Attest, DeviceCheck, reCAPTCHA를 통한 실제 증명(attestation).** 로컬 App Check는 디버그 토큰을 사용합니다.
- **제한된 사용 토큰과 재사용 방지.** `consumeAppCheckToken: true`인 callable은 501 `APP_CHECK_REPLAY_UNSUPPORTED`로 거부되고, `verifyToken(token, { consume: true })`은 `app-check/unimplemented`로 응답하므로, 프로덕션이라면 소비했을 토큰으로 테스트가 통과할 수 없습니다.
- **데몬보다 오래 살아남는 토큰.** 토큰은 하나의 데몬 인스턴스에 속한 키로 서명됩니다([Callable 함수](#callable-함수) 참고).
- **Python callable**에는 추가 제한이 있습니다. [Cloud Functions (Python)](../functions-python/#프로덕션-및-firebase-cli와의-차이)을 참고하십시오.

두 가지 동작은 위에서 설명한 부분에서 다릅니다.

- `verifyToken`은 모든 프로필에서 등록되지 않았거나 비활성화된 앱의 토큰을 거부합니다. 프로덕션은 만료될 때까지 받아들입니다([Admin SDK로 검증](#admin-sdk로-검증-getappcheckverifytoken)).
- `"loopback"`에서는 `enforced` Storage 서비스가 토큰 없이 로컬의 브라우저가 아닌 요청을 허용합니다([서버 측 코드의 Storage 요청](#서버-측-코드의-storage-요청)).
