Fireemu는 Firebase Realtime Database를 `127.0.0.1:9000`에서 제공합니다. REST API, SDK가 사용하는 실시간 프로토콜, Security Rules, 그리고 Firebase CLI 형식의 내보내기와 가져오기를 지원합니다. 기록된 케이스에 대해서는 프로덕션과 비교 검증되었으며, 그 밖의 프로덕션 호환성은 검증되지 않았습니다([프로덕션과의 차이](#프로덕션과의-차이) 참조).

또한 공식 에뮬레이터(firebase-database-emulator v4.11.2, firebase-tools 15.28.2가 실행하는 버전)와도 비교되었으나 아직 동등성 주장은 없으므로, [호환성 계약](../../compatibility/)에는 이 비교가 열려 있는 공백으로 나열되어 있습니다. 프로덕션이 관측되지 않은 곳에서 공식 에뮬레이터를 따른 동작은 바뀔 수 있습니다([잠정 동작](#잠정-동작) 참조).

## 연결

### 데이터베이스 시작

데이터베이스는 선택하거나 구성하면 시작됩니다. 다음 중 어느 것도 없으면 기본 실행은 9000번 포트를 비워 둡니다.

- `--only database` (다른 서비스와 함께: `--only auth,firestore,database`);
- `firebase init`이 기록하는 `firebase.json`의 `emulators.database`;
- `fireemu.toml`의 `daemon.databasePort` 또는 `--database-port`.

```sh
npx fireemu exec --only database -- npm test
```

```json
{
  "emulators": { "database": { "port": 9000 } }
}
```

포트가 사용 중이면 시작이 중단됩니다(`error: bind 127.0.0.1:9000: Address already in use`). 9000은 PHP-FPM의 기본 포트이기도 하므로, `--database-port` 또는 `emulators.database.port`로 다른 포트를 고르거나 `--only`로 데이터베이스를 제외하십시오.

시작 배너는 주소와 적용 중인 규칙을 보여 줍니다.

```text
  database:         127.0.0.1:9000   FIREBASE_DATABASE_EMULATOR_HOST=127.0.0.1:9000
  database rules:   demo-app-default-rtdb <- ./database.rules.json; another instance: every request is allowed (database.defaultAccess = open, default)
```

### SDK가 에뮬레이터를 가리키게 하기

`fireemu exec`는 실행하는 명령에 `FIREBASE_DATABASE_EMULATOR_HOST`를 설정하며, Admin SDK가 이를 읽습니다([환경 변수](../../reference/environment-variables/) 참조).

`exec`는 firebase-tools와 같이 `databaseURL`이 `https://<project>.firebaseio.com`인 `FIREBASE_CONFIG`도 설정합니다. 따라서 옵션 없이 초기화한 Admin SDK 앱은 `<project>-default-rtdb`가 아니라 `<project>` 인스턴스를 읽고 씁니다. 단일 규칙 형식과 아래의 클라이언트 예제는 `<project>-default-rtdb`를 사용합니다. 클라이언트와 인스턴스를 공유하려면 `initializeApp`에 `databaseURL: 'https://<project>-default-rtdb.firebaseio.com'`을 전달하십시오.

웹과 모바일 클라이언트는 명시적으로 연결합니다.

```js
import { initializeApp } from 'firebase/app';
import { getDatabase, connectDatabaseEmulator } from 'firebase/database';

const app = initializeApp({ projectId: 'demo-app', databaseURL: 'https://demo-app-default-rtdb.firebaseio.com' });
const db = getDatabase(app);
connectDatabaseEmulator(db, '127.0.0.1', 9000);
```

### 인스턴스

데이터베이스 인스턴스는 네임스페이스입니다. 요청은 공식 에뮬레이터와 같이 `ns` 쿼리 매개변수 또는 호스트 이름의 첫 번째 레이블로 인스턴스를 선택합니다. `demo-app-default-rtdb`는 프로젝트 `demo-app`의 기본 인스턴스입니다. ID 토큰은 해당 프로젝트를 기준으로 검사하며, 다른 이름의 인스턴스는 데몬의 프로젝트를 기준으로 검사합니다. 세션 reset과 세션 스냅샷은 `<project>`와 `<project>-default-rtdb`를 대상으로 합니다.

## 제공되는 기능

- REST API(`.json` 경로): 읽기, 쓰기, 업데이트, push ID, ETag를 사용하는 조건부 요청, `shallow`, `print`, `format=export`, 쿼리, 이벤트 스트림(`Accept: text/event-stream`).
- WebSocket과 롱 폴링(`forceLongPolling()`) 위의 실시간 프로토콜: 리슨, 쿼리, 트랜잭션, 서버 값.
- `onDisconnect` 쓰기(`set`, `update`, `remove`, `cancel`). 연결이 어떤 식으로든 끝날 때 실행되며, 그 시점에 서버 값이 확정된 하나의 업데이트로 실행됩니다. 공식 에뮬레이터가 종료될 때 이를 실행하지 않는 것과 같이 Fireemu 자체가 종료될 때는 실행되지 않으며, 세션 reset은 reset 대상 프로젝트에 등록된 쓰기를 버립니다.
- [Security Rules](#security-rules), `/.settings/rules.json`, `/.inspect/databases.json`, 쓰기의 `disableTriggers`.
- [내보내기, 가져오기, 세션 스냅샷](#내보내기-가져오기-스냅샷).

저장소의 `tools/sdk-smoke-database`는 고정된 `firebase`와 `firebase-admin` SDK로 이 기능들을 실행하고, 그 결과를 공식 에뮬레이터의 기록과 비교합니다.

### REST 옵션

- 일반 REST 읽기는 `timeout`을 최대 15분의 양의 기간(예: `1s`, `2seconds`, `3min`)으로 검증합니다. 이는 요청 데드라인을 설정하지 않고 옵션만 검증합니다. 쓰기, shallow 읽기, 조건부 읽기는 이를 무시합니다. 잘못된 기간은 거부되며, 기간 오버플로는 500을 반환할 수 있습니다.
- `shallow=true`는 `limitToFirst`와 일반 텍스트 `startAfter`를 받아들이고, `limitToLast`, `startAt`, `endAt`, `orderBy`는 거부합니다.
- 읽기는 `writeSizeLimit`을 무시하고, 쓰기는 `format`을 무시합니다.
- 조건부 응답은 ETag를 유지합니다. `if-none-match` PUT은 `print=silent`에서도 ETag를 포함하며, `X-Firebase-ETag: true`는 304, 거부된 조건부 PUT(412), POST에서도 ETag를 요청합니다.
- `strict`에서 경로의 잘못된 퍼센트 이스케이프는 `application/octet-stream`과 `Bad request.`로 400을 반환합니다. `emulator` 프로필은 공식 에뮬레이터의 응답을 유지합니다.

### 다중 경로 쓰기의 순서

하나의 다중 경로 쓰기(REST `PATCH`, SDK `update()`, 종료되는 연결의 `onDisconnect` 쓰기)의 엔트리는 공식 에뮬레이터의 순서로 연결의 리슨에 도달합니다. 엔트리가 네 개까지는 전송 또는 등록된 순서이고, 다섯 개부터는 키의 해시 순서입니다. 쓰인 위치 또는 그 상위 위치의 리슨이 먼저 받습니다. 프로덕션 기록 하나가 키 여섯 개의 집합에 대해 일치하며, 다른 형태는 공식 에뮬레이터를 따르고 프로덕션에서 관측된 적이 없습니다.

## Security Rules

Rules는 REST, 이벤트 스트림, 실시간 프로토콜 전반에서 `.read`, `.write`, `.validate`, `.indexOn`과 `auth`, `now`, `root`, `data`, `newData`, `query`, `$` 변수를 지원합니다.

### Rules 로드

Firebase CLI와 같이 `firebase.json`에 규칙 파일을 지정합니다. 단일 형식은 파일 하나를 기본 인스턴스 `<project>-default-rtdb`에 로드합니다.

```json
{
  "database": { "rules": "database.rules.json" }
}
```

배열 형식은 각 엔트리를 해당 `instance`에 로드하거나, `.firebaserc`의 배포 `target`에 속한 인스턴스에 로드합니다.

```json
{
  "database": [
    { "instance": "demo-app-default-rtdb", "rules": "database.rules.json" },
    { "target": "audit", "rules": "audit.rules.json" }
  ]
}
```

로드되지 않는 규칙 파일은 firebase-tools가 멈추는 것과 같이 파일, 줄, 열을 보여 주며 시작을 중단시킵니다. 변경된 파일은 Fireemu가 실행되는 동안 다시 로드됩니다. 로드되지 않는 변경은 적용 중인 규칙을 유지하고 그 이유를 출력합니다.

`GET`과 `PUT /.settings/rules.json?ns=<instance>`는 관리자 자격 증명으로 인스턴스의 규칙을 읽고 교체하며, `@firebase/rules-unit-testing`이 규칙을 로드하는 방식이 이것입니다. 이 경로는 Firestore 및 Storage 규칙 경로와 같이 루프백 피어를 요구합니다. 루프백이 아닌 피어는 자격 증명을 평가하기 전에 403을 받으며, 반복된 선행 슬래시와 퍼센트 인코딩된 `.settings` 경로에도 같은 제한이 적용됩니다.

### 규칙 파일의 오류

유효하지 않은 Rules를 로드하면 첫 번째 구문 오류, 중복 키 오류, 잘못된 인덱스 이름 오류를 보고합니다. 파싱되는 문서의 경우 타입과 이름 오류는 규칙 순서(`.read`, `.write`, `.validate`, 그다음 파일 순서의 이름 있는 자식, 마지막으로 와일드카드 자식)로 보고되며, 수집에는 제한이 있습니다. 지원되지 않는 JavaScript 구문은 여전히 실패합니다. 더 많은 형태를 파싱하는 것은 오류 메시지를 개선할 뿐 그 형태를 활성화하지 않습니다. 기록된 케이스가 모든 잘못된 입력을 보증하지는 않습니다.

### 비교된 범위

공식 에뮬레이터와의 비교는 REST 읽기와 쓰기, 범위/개수 쿼리가 있거나 없는 이벤트 스트림, 쿼리가 없는(`q`가 없거나 비어 있는) 실시간 리슨을 다룹니다. 쿼리가 있는 모든 WebSocket 리슨 형태를 보증하지는 않으며, 롱 폴링은 공용 실시간 세션 동작을 사용합니다.

유한한 기록된 프로덕션 REST Rules, 쿼리 의존 Rules, 쿼리 바운드 케이스는 기록된 롱 폴 트랜잭션 프레임과 함께 두 프로필 모두에서 재생됩니다. 이 관측은 기록된 요청을 다루며 모든 규칙, 쿼리, 전송 형태에 대한 동등성을 보증하지 않습니다.

### 이벤트 스트림과 리슨

쿼리가 범위를 제한하거나 개수를 제한하는 이벤트 스트림은 그 쿼리로 판정됩니다. 쿼리가 읽기를 정렬하기만 하는 스트림은 모든 데이터를 읽으며, 공식 에뮬레이터와 같이 쿼리가 없는 스트림으로 판정되어 인덱스가 필요하지 않습니다.

규칙 변경, 데이터에 의존하는 `.read`의 허용 범위를 바꾸는 쓰기, 클라이언트의 로그인 또는 로그아웃은 규칙이 더 이상 허용하지 않는 리슨과 이벤트 스트림을 취소합니다.

### `onDisconnect` 쓰기와 Rules

`onDisconnect` 쓰기는 등록할 때와 연결이 끝날 때 모두 검사됩니다.

- **등록 시.** `set`은 하나의 쓰기로, `update`는 엔트리별로 각각 현재 트리를 기준으로 검사합니다. 어느 한 엔트리라도 실패하면 등록이 거부됩니다.
- **연결 해제 시.** 대기 중인 각 엔트리를 먼저 그 시점의 트리를 기준으로 개별적으로 검사합니다. `.write` 또는 `.validate`로 거부된 엔트리는 버려집니다. 남은 엔트리는 다시 하나의 업데이트로 함께 검사되며, 이 결합 검사가 실패하면 어느 것도 적용되지 않습니다.

기록된 프로덕션 케이스에서, 숫자 priority로 등록된 onDisconnect 값의 자식을 취소하면 관련 없는 쓰기를 포함해 연결의 업데이트 전체가 버려집니다. 두 번의 기록된 라운드는 자식 취소 후 재등록, 중첩 priority, 문자열 priority도 다루며, 각 형태의 기록된 두 라운드가 각 프로필에서 재생되었습니다. 그 밖의 priority 및 취소 형태는 프로덕션에서 검증되지 않았습니다.

### 자격 증명

| 자격 증명 | `emulator` 프로필 | `strict` 프로필 (기본값) |
|---|---|---|
| `Authorization: Bearer owner` 또는 `access_token=owner` (에뮬레이터 소유자 자격 증명) | 관리자. 규칙이 적용되지 않음 | 관리자. 규칙이 적용되지 않음 |
| 그 밖의 단일 `Authorization: Bearer` 또는 `access_token` | 공식 에뮬레이터와 같이 관리자. `network.allowNonLoopbackHosts`가 공개하지 않는 한 리스너는 루프백에 있으며, 먼저 [CI와 컨테이너](../../guides/ci-and-containers/)를 참조 | 401로 거부. 이벤트 스트림이 아닌 데이터 경로의 읽기는, 측정 당시 프로덕션이 응답한 대로 본문이 `Unauthorized request.`임(빈 Bearer는 `Permission denied`로 유지) |
| Fireemu의 Auth가 서명한 `auth=<ID token>` | 토큰이 지목하는 사용자, 사용자 지정 클레임은 `auth`의 멤버로 전달 | 토큰이 해당 인스턴스의 프로젝트용이면 토큰이 지목하는 사용자 |
| `auth=<unsigned ID token>` (`@firebase/rules-unit-testing`, `mockUserToken`) | `auth.allowUnsignedIdTokens`가 `true`(기본값. `productionExact`에서는 `false`이며 이때 익명이 됨)인 동안, 공식 에뮬레이터가 읽는 방식대로 토큰의 `sub`가 지목하는 사용자(어떤 프로젝트를 지목하든, `aud`가 있든 없든) | `auth.allowUnsignedIdTokens`가 `true`(기본값. `productionExact`에서는 `false`)인 동안, 토큰이 `createMockUserToken` 형태이고 인스턴스의 프로젝트를 audience로 가지면 토큰이 지목하는 사용자 |
| Fireemu가 검증할 수 없는, RS256 또는 HS256으로 서명된 `auth=<token>` | 공식 에뮬레이터가 읽는 방식대로, 토큰이 비어 있지 않은 서명, 인스턴스의 프로젝트인 `aud`, 미래의 `exp`, 존재하는 테넌트(테넌트를 지목하는 경우)를 가지고, 서명되지 않은 토큰이 허용되며 Fireemu의 Auth가 자체 토큰을 서명하지 않는 동안 클레임이 지목하는 사용자. 그 외에는 익명 | 401로 거부 |
| 그 밖의 `auth=` 값 | 익명 | 401로 거부. 단, 이벤트 스트림이 아닌 데이터 경로의 읽기에서 불투명한 값(영문자와 숫자 1~128자, `null`이나 `owner`가 아니며 쿼리를 디코딩한 뒤 판정)은 측정 당시 프로덕션이 응답한 대로 인증되지 않은 것으로 처리됨. 규칙이 모두에게 여는 경로는 읽히고 보호된 경로는 계속 거부됨 |

이 표를 적용하기 전에 Fireemu는 두 프로필 모두에서 모호한 HTTP 요청을 400으로 거부합니다. 반복된 쿼리 매개변수(`auth`와 `access_token` 포함), 둘 이상의 `Authorization` 헤더, 쿼리 자격 증명과 `Authorization` 헤더의 조합이 해당합니다. 동일한 자격 증명이 반복된 경우도 모호한 것으로 취급합니다. 공식 에뮬레이터는 대신 하나의 값을 선택하므로, 이는 나열된 차이입니다.

`auth_variable_override`(Admin SDK가 `databaseAuthVariableOverride`에 대해 보내는 값)를 함께 가진 관리자 REST 요청은, 기록된 케이스에서 프로덕션이 평가한 것과 같이 규칙이 그 `auth` 값으로 평가합니다. `null`은 인증되지 않은 것으로 읽히며, 잘못된 형식이거나 객체도 `null`도 아닌 override는 거부됩니다.

`firebase emulators:export`가 읽는 `/.inspect/databases.json`은 `emulator` 프로필에서는 누구에게나 응답하고, `strict`에서나 잠긴 데이터베이스에서는 `owner` 자격 증명에만 응답합니다.

### 규칙이 없는 인스턴스

규칙 파일이 없는 인스턴스는 `database.defaultAccess`를 따릅니다.

- `"open"` (두 프로필의 개발 기본값): 공식 에뮬레이터가 규칙 없는 데이터베이스를 제공하는 것과 같이 모든 요청이 허용됩니다.
- `"locked"` (`productionExact`의 기본값, `strict` 프로필 전용): 잠금 모드의 새 프로덕션 데이터베이스가 관리자만 허용하는 것과 같이 `owner` 자격 증명만 읽고 쓸 수 있습니다. 로그인한 사용자를 포함해 다른 모든 자격 증명은 401로 거부됩니다.

### `@firebase/rules-unit-testing`으로 단위 테스트

`initializeTestEnvironment`는 전달한 규칙을 `/.settings/rules.json`으로 로드하고, `authenticatedContext()`는 서명되지 않은 모의 토큰을 보내며, `withSecurityRulesDisabled()`와 `clearDatabase()`가 제공됩니다.

```js
import { initializeTestEnvironment, assertFails, assertSucceeds } from '@firebase/rules-unit-testing';
import { readFileSync } from 'node:fs';

const [host, port] = process.env.FIREBASE_DATABASE_EMULATOR_HOST.split(':');
const testEnv = await initializeTestEnvironment({
  projectId: 'demo-app',
  database: { host, port: Number(port), rules: readFileSync('database.rules.json', 'utf8') },
});
const alice = testEnv.authenticatedContext('alice').database();
await assertSucceeds(alice.ref('users/alice').set({ name: 'Alice' }));
await assertFails(alice.ref('users/bob').set({ name: 'Mallory' }));
await testEnv.cleanup();
```

`npx fireemu exec --only database -- node test.mjs`로 실행하십시오.

프로덕션이 서명되지 않은 토큰을 거부하는 동작을 테스트하려면 `auth.allowUnsignedIdTokens`를 `false`로 설정하거나 [`productionExact`](../../guides/profiles/)를 설정하십시오. 그러면 실시간 연결이 모의 토큰을 거부하고(`invalid_token`) SDK가 계속 재시도하므로, `authenticatedContext()`의 읽기 또는 쓰기는 실패하는 대신 끝나지 않습니다. REST(`?auth=<token>`이 401로 응답)로 거부를 확인하거나 assertion에 타임아웃을 지정하십시오.

### Rules 커버리지

`/.inspect/coverage?ns=<instance>`(HTML 뷰어)와 `/.inspect/coverage.json?ns=<instance>`는 공식 에뮬레이터와 같이, 로드된 규칙의 각 표현식이 낸 결과를 보고합니다.

- 수집은 항상 켜져 있으며 기록된 결과당 해시 조회 한 번의 비용이 듭니다.
- 긴 실행도 빠르고 작게 유지되도록, 각 표현식은 처음 64개의 서로 다른 결과(문자열 값은 최대 64 KiB)만 보관하고, 이후의 새 결과는 나열되는 대신 `values-omitted`에 집계됩니다.
- `data`와 `root` 같은 스냅샷 값은 평가할 때마다 새로운 ID를 가지므로 목록이 빨리 찹니다.
- 변경된 규칙을 로드하면 새 보고서가 시작되고, 같은 텍스트를 다시 로드하면 보고서가 유지됩니다.

## 내보내기, 가져오기, 스냅샷

`emulators:export`, `--export-on-exit`, Hub의 내보내기는 데이터를 가지고 있거나 가져온 모든 인스턴스에 대해 `GET /.json?format=export`의 내보내기 형식(priority 유지)으로 `database_export/<instance>.json`을 기록하고, firebase-tools가 기록하는 `firebase-export-metadata.json`의 `database` 섹션도 함께 기록합니다. 같은 데이터에 대해 파일은 Firebase CLI의 파일과 바이트 단위로 동일하며, 각 도구는 서로의 내보내기를 가져올 수 있습니다.

```sh
npx fireemu exec --only database --export-on-exit ./emulator-data -- npm test
npx fireemu exec --only database --import ./emulator-data -- npm test
```

```text
emulator-data/
  firebase-export-metadata.json
  database_export/
    demo-app-default-rtdb.json
```

`--import`는 firebase-tools와 같이 명령이 시작되기 전에 각 파일을 `disableTriggers=true`와 함께 `owner` 자격 증명으로 기록합니다.

- 파일 이름을 소문자로 바꾼 것이 인스턴스입니다.
- 잘못된 인스턴스 이름의 파일이나, 데이터베이스가 거부할 파일(잘못된 JSON, 잘못된 키, 너무 깊게 중첩된 데이터)은 다른 제품의 데이터가 설치되기 전에 시작을 중단시킵니다.
- 데이터베이스가 선택되지 않은 경우 내보내기의 데이터베이스 섹션은 안내와 함께 건너뜁니다.

세션 스냅샷과 reset은 세션 프로젝트의 인스턴스를 포함합니다. 복원 또는 reset은 열려 있는 리스너와 이벤트 스트림에 전달되고, 복원된 데이터에서 규칙이 더 이상 허용하지 않는 것들은 취소되며, 해당 인스턴스에 등록된 `onDisconnect` 쓰기는 버려집니다.

[테스트 월드](https://github.com/fireemu/fireemu/blob/main/docs/test-worlds.md)에서는 `services`에서 `database`를 선택하십시오. `world.endpoints.database`와 `FIREBASE_DATABASE_EMULATOR_HOST`가 이를 가리키며, 데이터는 내보내기, 가져오기, reset 이후에도 유지됩니다.

## 로컬 Functions 트리거

로컬 v1 및 v2 데이터베이스 핸들러는 자신의 프로젝트, 인스턴스, 참조 패턴에 한정된 create, update, delete, write 이벤트를 받습니다. 러너가 Firebase SDK 스냅샷 객체를 제공합니다.

- 변경되지 않은 쓰기는 변경 이벤트를 내보내지 않습니다.
- 소스 변경과 그에 예약된 이벤트 배치는 함께 커밋됩니다.
- 어떤 트리거 참조에도 도달할 수 없는 쓰기는 스냅샷을 캡처하지 않고 적용되므로, 한 경로의 트리거가 다른 곳의 쓰기에 비용을 추가하지 않습니다.
- 세션 reset은 소스 데이터를 지우고 Functions epoch를 종료하는 동안 동시 데이터베이스 변경을 배제합니다.

### 이벤트 큐가 가득 찼을 때

- 로컬 이벤트 큐가 가득 찬 동안, 이벤트가 빈 큐에는 들어갈 수 있는 쓰기는 503으로 거부되며, 전달이 진행되어 큐가 비워진 뒤 재시도하면 성공합니다.
- 이벤트가 절대 들어갈 수 없는 쓰기(예: `/users/{uid}` 트리거 아래에 자식 5,000개를 한 번에 `PUT`하는 경우처럼 직렬화된 이벤트가 4096개 또는 64 MiB를 넘는 경우)는 프로덕션이 적용하는 것과 같이, 큐의 상태와 관계없이 이벤트 없이 적용됩니다.

### 이벤트 크기

- **`emulator` 프로필.** 호출 프레임(16 MiB)보다 큰 이벤트는 그것만 버려지고 쓰기의 다른 이벤트는 전달됩니다. 처음 버려질 때 경고를 출력하며, 버려진 각 이벤트는 리소스 진단에서 `admission.database_fanout_dropped`로 집계됩니다.
- **`strict` 프로필.** 등록된 트리거 참조에 도달하는 쓰기의 이벤트(쓰기 이전의 노드에 델타를 더한 것, 압축 JSON 기준)가 1,048,576바이트(1 MiB)보다 크면 `400`과 `This request would cause a function payload exceeding the maximum size allowed.`로 거부되고 아무것도 적용되지 않습니다. 프로덕션이 2 MiB 값에 대해 그렇게 했습니다. SDK 연결은 같은 문구와 함께 `invalid_parameters`로 응답하며, 이 형식은 기록되지 않았습니다.

strict 임계값은 2026-11-08과 2026-11-09의 기록에서 나왔습니다. 1,023,9xx바이트의 이벤트는 수락되어 전달되었고 1,049,9xx바이트의 이벤트는 거부되었습니다. 프로덕션 문서는 이벤트당 1 MB라고 하므로 1 MiB를 사용합니다. 이 두 크기 사이의 정확한 임계값과 이벤트 크기를 세는 방식은 검증되지 않았습니다.

### Priority

프로덕션과 같이 strict 이벤트는 priority를 포함하지 않습니다. 쓰기 이전 노드에는 priority가 없고, 생성된 노드의 델타는 단순 값이며, priority만 쓰는 경우 델타 `{".priority": n}`을 보냅니다. emulator 프로필은 기존에 보내던 이벤트를 유지합니다.

### 리전

로컬 인스턴스는 `us-central1`에 있습니다. 다른 리전의 2세대 트리거는 실행되지 않으며, 공식 에뮬레이터가 경고하는 것과 같이 로드 시 경고가 이를 알려 줍니다. 프로덕션에서는 자신의 리전에 있는 인스턴스에 대해서만 실행됩니다.

### 이벤트 메타데이터와 기록된 내용

프로덕션 관측은 v1 및 v2 핸들러에 대한 관리자 및 미인증 쓰기의 고정된 시퀀스를 다룹니다. 기록된 전달에 대해 strict 프로필은 관측된 이벤트 ID, 밀리초 타임스탬프, 소스 및 인증 메타데이터 형식을 사용합니다.

이벤트 ID는 구성에 지정된 `daemon.seed`와 이벤트 시퀀스에 대해 결정적이므로, 같은 시드를 반복하면 같은 ID가 재생됩니다. `daemon.seed`가 없으면 데몬이 시작될 때마다 자체 세션을 생성하므로, 재시작해도 이전 실행의 ID가 반복되지 않습니다.

추가 기록은 REST와 웹 SDK를 통한 이메일/비밀번호 사용자의 쓰기 12건을 다루며, 상위 경로 쓰기와 다중 경로 쓰기, 호출 실패 후의 재전달을 포함합니다. strict 프로필은 기록된 프로덕션 메타데이터를 사용하고, emulator 프로필은 문서화된 공식 에뮬레이터 이벤트 형태를 유지합니다. 전달 지연, 재시도 타이밍, 핸들러 간 순서, 다른 제공자, 기록되지 않은 쓰기 또는 핸들러 형태는 검증되지 않았습니다.

[Emulator UI](../../guides/ui/)의 Realtime Database 페이지에서는 다음 네 가지를 할 수 있습니다.

- 로컬 관리자로서 데이터를 교체, 패치, 삭제합니다(따라서 이러한 편집은 클라이언트 권한을 테스트하지 않습니다).

## 프로덕션과의 차이

Fireemu는 기록된 케이스에 대해서만 프로덕션과 비교되었습니다.

### 기록된 케이스

- **REST.** PUT, GET, PATCH의 값과 priority, 유한한 POST 생성 키와 읽기 확인, DELETE, `shallow`, `print=silent`와 작은 `writeSizeLimit` 형태, `format=export`, `startAt`, `endAt`, `startAfter`, `endBefore`, `equalTo`, `limitToFirst`, `limitToLast`를 포함한 유한한 `orderBy` 쿼리 바운드 형태, ETag와 `if-match`, 기록된 오류. 기록된 범위에는 REST 옵션 및 거부 케이스 72건(`timeout`, `$priority`, 메서드 override, 콜백, 다운로드 포함)과 생성된 잘못된 REST 자격 증명도 포함됩니다.
- **Rules.** 유한한 Rules 로드, `.validate`, 캐스케이드, `data`/`newData`/`root`, 쿼리 의존 Rules 케이스와, 소유자 및 UID `.read`와 `.write` 평가: Rules 케이스 70건, 추가 Rules 문서 7건, 그리고 `query.endBefore`, `query.isOrderByChild()`, `OrderByKey`, `OrderByValue`, `OrderByPriority`, `http.encodeURL()`, 호출 없는 메서드 읽기, 삼항 호출 대상에 대한 문서 9건과 그 아래의 읽기 및 쓰기 33건.
- **이벤트 스트림.** 익명 이벤트 스트림.
- **웹 SDK.** 값 리스너, 대기 중인 쓰기가 있는 재연결, 쿼리 범위 구독 해제와 취소가 있는 두 `orderByChild` 윈도우의 child 및 value 이벤트 순서, 서버 값과 발동 전 Rules 변경을 포함한 `onDisconnect`의 set, remove, update, cancel, 재등록, 기록된 숫자 priority child 취소 케이스와 기록된 세 가지 재등록, 중첩 priority, 문자열 priority 형태, 트랜잭션 스케줄 하나, WebSocket과 롱 폴링 위의 이메일/비밀번호 Auth. 추가 기록은 key, priority, value 범위, `equalTo` 윈도우에 대한 `prevName`을 가진 SDK child 이벤트, 동률 값에서의 키 바운드, 부모/자식 리스너 팬아웃, 존재하지 않는 노드와 객체에 대한 트랜잭션 및 중단된 트랜잭션, WebSocket과 롱 폴링 위의 윈도우 및 존재하지 않는 경로의 `get`을 다룹니다.
- **Admin SDK.** Node Admin SDK는 사용자 OAuth 액세스 토큰으로 deny-all Rules 아래에서 WebSocket 위에 기록되었으며, 서비스 계정 자격 증명은 주장하지 않습니다.
- **Functions 트리거.** 기록된 관리자 및 미인증 쓰기에 대한, 두 세대의 RTDB 트리거 Functions created, updated, deleted, written 핸들러([로컬 Functions 트리거](#로컬-functions-트리거)에서 설명한 유한한 최종 사용자 트리거 전달).

추가로 유한한 서버 값, Rules 언어, Rules 메서드, Rules 연산자 케이스가 기록되어 두 프로필 모두에서 재생되었으며, 기록되지 않은 입력에 대한 동등성을 보증하지 않습니다.

### 알려진 차이

기록된 범위 안에서 다음 차이가 알려져 있습니다.

- limit이 없는 범위 읽기, shallow 읽기, PATCH 응답은 공식 에뮬레이터의 맵 순서를 사용합니다. 엔트리가 네 개까지는 삽입 순서를 유지하고, 그보다 큰 맵은 키 해시를 사용합니다. PATCH는 pretty 및 콜백 출력을 포함해 중첩 응답에서 기록된 멤버 순서를 보존합니다. 프로덕션과의 일반적인 JSON 멤버 순서 동등성은 주장하지 않습니다.
- 연결을 닫지 않고 오프라인이 된 롱 폴링 클라이언트의 `onDisconnect` 쓰기는 유휴 연결이 끊길 때, 즉 마지막 요청으로부터 약 100초에서 105초 뒤에 실행됩니다. 프로덕션은 99.3초에서 104.0초 뒤에 실행했습니다.
- `strict`에서 이벤트 스트림은 `Connection: close`를 전달하며, HTTP/1.1 연결은 `cancel` 이벤트와 청크 응답의 종료 뒤에 닫힙니다. 기록된 이벤트 바이트는 프로덕션과 일치하지만, 기록된 프로덕션 응답은 전송 인코딩 없이 연결 종료로 구분되었던 반면 Fireemu는 네이티브 HTTP/1.1 청크 프레이밍을 사용합니다. 이 전송 프레이밍 차이는 소유자가 승인한 개발용 예외입니다(2026-10-31). 이벤트 내용, 취소, EOF는 기존 증거 요건의 적용을 계속 받습니다. `emulator` 프로필은 기존 연결 동작을 유지하며, 더 넓은 스트림 수명 주기 동작은 검증되지 않았습니다.
- 프로덕션의 Google 서명 Firebase ID 토큰은 허용되지 않습니다. Fireemu의 Auth가 발급한 토큰과 `owner` 자격 증명은 허용되며, `strict`는 다른 `gauth` 자격 증명을 프로덕션의 `permission_denied`로 거부합니다.

### 검증되지 않은 부분

위의 유한한 REST, Rules, SDK, 트리거 케이스가 기록되었습니다. 그 밖에는 다음과 같습니다.

- 다른 push ID 형태, 서버 값, 쿼리 바운드, 타임아웃, 쓰기 크기 옵션은 검증되지 않았습니다.
- 기록된 케이스를 넘어서는 Rules 검증, 캐스케이드, 스냅샷, 쿼리 멤버, 클레임, 인덱스 진단은 여전히 공식 에뮬레이터를 잠정 기준으로 사용합니다.
- 기록된 케이스를 넘어서는 SDK 이벤트, 트랜잭션, 다중 위치 업데이트, onDisconnect 형태, 서비스 계정 Admin 자격 증명, 그리고 더 넓은 Functions 트리거 전달과 타이밍은 주장하지 않습니다.

### 아직 지원되지 않는 항목

- Android, Apple, Unity, 그리고 Java와 Python Admin SDK는 현재 Node와 Web 범위 밖입니다.

### 제한

- 표현식은 최대 600단계까지 중첩됩니다. 길이에 관계없이 `&&`, `||`, `+` 체인은 한 번으로 셉니다. 이는 로컬 안전 예산이며, 공식 에뮬레이터 자체는 2,000단계에서 4,000단계 사이에서 실패합니다.
- 정규식 엔진의 단계 또는 깊이 예산을 넘는 `matches()` 호출은 오류이므로, 부정 여부와 관계없이 규칙은 false입니다.
- 프로덕션 문서와 같이 쓰기의 경로는 최대 768바이트, 데이터는 최대 32단계 깊이입니다.

### 잠정 동작

프로덕션이 관측되지 않은 곳에서는, 위에 나열한 알려진 차이를 전제로 기록된 공식 에뮬레이터 동작이 잠정 기준입니다. 이 비교는 프로덕션과의 동등성을 보증하지 않으며 프로덕션 관측 이후 바뀔 수 있습니다. 다음을 다룹니다.

- `1.0` 같은 숫자 형태;
- 동일한 값의 쓰기;
- priority;
- 거부 문구;
- 롱 폴링 프레이밍;
- `onDisconnect` 쓰기가 결합되는 방식;
- 각 프로필의 자격 증명;
- 정규식 방언;
- 공식 에뮬레이터가 쓰기 본문에서는 768바이트 키를 거부하지만 경로에서는 허용하는 경우;
- 결정화(determinize)할 수 없는 패턴.

## 공식 에뮬레이터와의 차이

공식 에뮬레이터와의 비교는 기록된 케이스로 제한됩니다. 나열된 지원되지 않는 구문 및 평가 케이스는 규칙이 로드될 때 거부되거나 규칙 오류를 일으킵니다. 이는 동등한 리소스 제한 허용을 보증하지 않습니다.

- 문자 클래스(이름, 공백, 공식 에뮬레이터의 리더가 건너뛰는 서식 문자)는 Java 21의 표를 사용합니다.
- 연산자와 메서드는 기록된 피연산자 타입에 대해 공식 에뮬레이터와 비교되었습니다.
- 객체는 공식 에뮬레이터와 같이 동일성으로 비교됩니다. `auth`와 `query`는 각각 자기 자신과 같습니다. 두 스냅샷은 같은 위치에서 트리의 같은 버전을 읽을 때 같습니다(`root`와 `data`는 쓰기 이전의 트리를, `newData`는 쓰기 이후의 트리를 읽음). 따라서 `/t/o`의 `data`는 `root.child('t').child('o')`와 같고, `newData`와는 같지 않습니다.
- 두 스냅샷끼리, 또는 `query`를 자기 자신과 직접 비교하는 것은 거기서와 같이 Rules가 로드될 때 여전히 거부됩니다. 삼항 연산자로 그 검사를 통과시키면 비교가 실행됩니다.
- `auth` 멤버에서 읽은 객체와 자식이 있는 위치에 대해 `val()`이 주는 값은 매번 새 객체이며 어떤 것과도 같지 않습니다.

### 정규식

공식 에뮬레이터는 `matches()` 패턴을 자체 방언, 즉 JavaScript도 RE2도 아닌 오토마톤 문법으로 읽습니다. Fireemu는 기록된 범위에서 그 문법을 따릅니다. 예를 들어 `a+?`는 (lazy 반복이 아니라) `(a+)?`를 의미하고, `/a|q/`는 `.*a|q.*`로 검색되며, `i` 아래에서 ASCII 패턴은 거기서와 같이 대소문자를 접지만 매칭 대상 문자열은 그대로 둡니다.

Fireemu가 아직 그 의미를 재현하지 못하는 구문은 오류이므로, 부정 여부와 관계없이 규칙은 false입니다. emulator 프로필은 아래 구문 대부분을 공식 에뮬레이터와 같이 읽고, strict 프로필은 프로덕션에 확인하지 않았으므로 모두 오류로 유지합니다.

| 구문 | 예 |
|---|---|
| `(?…)` 그룹. emulator 프로필은 리터럴 `?`로 시작하는 그룹으로 읽음(`/(?:a)/`는 `?:a`와 일치) | `/(?:a)/`, `/(?i)a/` |
| POSIX 클래스(어느 프로필도 읽지 않음) | `/[[:alpha:]]/` |
| 어디서든 `\W`와 `\D` (emulator 프로필이 읽음) | `/\W/`, `/[\D]/` |
| `\d`와 `\w` 이외의 이스케이프된 문자 또는 숫자 (emulator 프로필이 읽음) | `/\n/`, `/\x41/`, `/\1/` |
| 클래스 안의 이스케이프된 백슬래시 (emulator 프로필이 읽음) | `/[\\a]/` |
| 대안(alternative)을 시작하는 연산자, 또는 `^` 뒤의 한정자 (emulator 프로필이 읽음) | `/(|a)/`, `/^(a|*)$/`, `/^*/`, `/^{2}a/` |
| 패턴에 ASCII를 넘는 문자가 있는 `i` 플래그 (어느 프로필도 읽지 않음) | `/^é$/i`, `/[ａ-ｚ]/i` |
| 줄 바꿈 앞의 백슬래시 (emulator 프로필은 라인 피드로 읽음) | `/a\` 다음에 줄 바꿈, 그다음 `b/` |
| 백슬래시 뒤에 U+200B 같은 서식 문자가 있는 이스케이프된 문자 (거기서와 같이 서식 문자는 버려짐) | `/\` U+200B `u0061/` |
| 끝이 Basic Multilingual Plane을 넘는 클래스 범위 (emulator 프로필은 UTF-16 단위로 읽음) | `/[a-😀]/` |

emulator 프로필이 이 구문을 읽는 방식은 다음과 같습니다.

- `\W`와 `\D`는 공식 에뮬레이터의 오토마톤과 같이 문자열 언어의 여집합입니다. `\W`는 단어 문자 하나를 제외한 모든 문자열이므로, `'ab'`와 `''`는 `/^\W$/`와 일치하고 `'a'`는 일치하지 않습니다. 이를 포함한 클래스는 구성원의 언어 합집합(`[\Wa]`)이고, 부정 클래스(`[^\W]`)는 평소처럼 단일 문자입니다.
- `d`, `w`, `D`, `W` 이외의 이스케이프된 문자 또는 숫자는 그 문자 자체입니다(`A`은 `u0041`, `\b`는 `b`이므로, `/[\uD800-\uDFFF]/`는 `0`부터 `u`까지의 문자와 `D`, `F`의 클래스입니다).
- 그 밖에는 공식 에뮬레이터의 클래스 문법을 읽습니다. 끝이 시작보다 앞인 범위는 아무것도 포함하지 않고, `[\\a]`는 `a`를 포함하며, 닫는 괄호 앞의 `-`는 문자이고, 대안의 시작에 있는 한정자나 다른 연산자는 그 문자 자체입니다.
- 패턴을 UTF-16 단위로 읽으므로 Basic Multilingual Plane을 넘는 문자는 클래스 구성원 두 개이자 `.`에 대해 두 단위이며, 백슬래시 뒤의 캐리지 리턴, U+2028, U+2029는 라인 피드이고 U+FEFF와 U+0085는 그 자체입니다.

공식 에뮬레이터와 strict 프로필이 패턴을 다르게 읽는 곳에서 strict 프로필은 규칙을 허용하지 않고 거부합니다.

읽지 않는다고 표시된 구문은 두 프로필 모두에서 오류로 남으므로, emulator 프로필도 공식 에뮬레이터가 허용하는 구문을 거기서는 여전히 거부합니다. Fireemu가 거부하고 공식 에뮬레이터가 허용한 기록된 방언 코퍼스의 323개 행 중 252개는 이제 같은 결과로 판정되고 71개는 거부로 남으며, 모두 `i` 플래그와 ASCII가 아닌 텍스트가 있는 경우입니다(선언된 차이이며, Java 21의 대소문자 접기 표가 필요합니다).

`\s`, 닫히지 않은 클래스나 그룹, 중간의 이스케이프되지 않은 `^`를 포함해 기록된 구문 거부 케이스는 여기서도 공식 에뮬레이터와 같은 메시지로 거부됩니다. 기록된 별도의 결정화 리소스 케이스는 아래에서 설명합니다.

공식 에뮬레이터의 결정화 리소스 제한으로 거부된, 기록된 패턴 8개는 평가되지 않는 표현식 분기를 포함해 Fireemu가 규칙을 로드할 때도 거부됩니다. 이는 완전한 정규식 또는 프로덕션 동등성을 보증하지 않습니다. 이들은 결정화 거부("could not determinize efficiently", 공식 에뮬레이터의 오토마톤 라이브러리의 리소스 제한)를 포함합니다. 기록된 패턴에는 한 패턴 안에서 대안 그룹의 반복 횟수가 지정된 것이 여러 개 있는 경우가 포함됩니다. 프로덕션의 제한은 알려져 있지 않으며, 이러한 비교에서 프로덕션 동작을 추정하지 않습니다.

### 외톨이 서로게이트

- **문자열 리터럴에서.** 문자열 리터럴의 이스케이프된 외톨이 서로게이트(`'\uD83D'`)는 공식 에뮬레이터와 같이 로드되고 UTF-16 단위로 판정됩니다(`.length`, `+`, `==`, 순서 비교, 문자열 메서드. 커버리지 보고서는 이를 U+FFFD로 표시). 이를 포함하는 경로나 키는 아무것도 지목하지 않습니다. `child()`는 absent를 읽고, `hasChild`는 false이며, 인덱스는 정의되지 않고, Basic Multilingual Plane을 넘는 문자가 있는 문자열의 `replace('', to)`는 Java와 같이 쌍의 두 절반 사이에 `to`를 넣습니다. 프로덕션이 이러한 형태에 응답한 적이 없으므로 두 프로필 모두 공식 에뮬레이터를 따릅니다.
- **저장된 값에서 (emulator 프로필 전용).** JSON 문자열 값의 외톨이 서로게이트 이스케이프는, 공식 에뮬레이터가 저장하는 것과 같이 외톨이 서로게이트마다 하나의 `?`로 저장되고 유효한 쌍은 그대로 둡니다. 이는 쓰기 본문(`PUT`, `PATCH`, `POST`, 중첩 값, `.value`, `.priority` 포함), WebSocket 프레임, 가져오기 파일에 적용되며, 쿼리의 바운드(`startAt="\ud83d"`, 리슨의 `sp`와 `ep`)도 같은 방식으로 `?`를 읽습니다. 이를 포함하는 키는 두 프로필 모두에서 거부되고, 이를 포함하는 WebSocket 경로는 `Invalid token in path`로 응답합니다. strict 프로필은 이전과 같이 이 모두를 거부하며, 프로덕션에는 확인하지 않았습니다.
- **토큰 클레임과 `authvar`에서 (어느 프로필도 읽지 않음, 선언된 차이).** 클레임에 외톨이 서로게이트가 있는 토큰(`"x":"\ud83d"`, 클레임 이름 포함)과, 이를 포함하는 `gauth` 프레임의 `authvar`가 해당합니다. 공식 에뮬레이터는 클레임의 서로게이트를 Java 문자열로 유지하며(`auth.token.x == '\uD83D'`이 성립) authvar 객체를 그대로 돌려줍니다. 여기서 strict 프로필은 그런 토큰에 401로 응답하고, emulator 프로필은 요청을 익명 요청으로 판정하며, authvar에 외톨이 서로게이트가 있는 `gauth` 프레임은 연결 오류가 됩니다.
- **WebSocket 경로와 병합 키에서.** WebSocket 프레임 경로의 외톨이 서로게이트는 (`.priority` 포함) 유효한 경로가 될 수 없습니다. 프레임은 `Invalid token in path`로 응답하며 아무것도 쓰거나 등록하거나 취소하지 않습니다. 키가 유효한 경로가 아닌 WebSocket 병합 엔트리는 emulator 프로필에서 `invalid_parameters`(`Invalid token in path`, `Empty strings are not valid keys`, 또는 경로 길이와 깊이 문구)로 응답하며, strict 프로필은 이전과 같이 연결 오류로 응답합니다. 잘못된 `onDisconnect` 병합 엔트리 키는 여전히 연결 오류를 일으킵니다.

### 평가 예산

단일 규칙 평가가 2^30 단위를 넘는 작업을 하면 여기서도 오류입니다. 작업은 다음과 같이 부과됩니다.

- 규칙이 읽거나, 연결하거나, 비교하거나, 검색하거나, 변환하거나, 치환하는 모든 문자열은 그 길이만큼;
- 클레임 또는 중첩 값의 복사는 그 크기만큼;
- `child`, `hasChild`, `hasChildren`, `parent()`로 만들거나 줄인 위치는 키의 바이트 수만큼.

이는 이차 시간의 `contains`, 긴 저장 문자열의 반복 연결, 계속 반복해서 만드는 경로를 막습니다. 10 MiB 문자열에 대한 검색 13회는 허용되고, 50회는 맞으며 52회는 맞지 않습니다(알려진 제한: 부정 여부와 관계없이 규칙이 거부됨). Rules 코퍼스는 한 번의 평가에서 최대 628 단위를 사용합니다.

이 한도는 평가당입니다. 하나의 요청이 많은 평가를 실행할 수 있으며(쓰기는 쓰는 각 자식을 검증), 요청 전체에 대한 제한과 실제 경과 시간 제한은 없으므로 느린 규칙은 계속 느립니다. 정규식 매처에는 `matches` 호출당 200,000단계라는 자체 한도가 있습니다.

규칙이 치환, 연결, 대소문자 변환으로 만드는 문자열이 2^26 단위(UTF-8 연산은 보수적으로 바이트를, UTF-16 연산은 코드 단위를 셈)를 넘으면 여기서 오류이므로, 부정 여부와 관계없이 규칙은 false입니다. 이는 `replace('', '0123456789')`를 열 번 연결한 규칙이 수십 기가바이트를 할당하는 것을 막습니다. 공식 에뮬레이터는 힙이 자체 한도를 결정합니다. 512 MB에서 그런 단계 7개(약 3,900만 단위)에는 응답했고 8번째에서 내부 오류(500)로 실패했습니다.

### 쿼리 변수와 메서드

- `query.orderBy`는 두 프로필에서 모두 로드됩니다. 읽기가 자식으로 정렬하면 자식 정렬(`query.orderBy == 'a/b'`)이고, 그렇지 않으면 `OrderByKey`, `OrderByValue`, `OrderByPriority`(일반 REST 읽기는 키로, 스트림과 리슨은 priority로 정렬)이며, 쓰기, 검증, shallow 읽기에서는 null입니다. priority에 의한 정렬은 자식 `.priority`에 의한 정렬이므로, 거기서는 `query.orderBy == '.priority'`와 `query.isOrderByChild('.priority')`가 성립합니다.
- `query.endBefore`는 끝 바운드(미포함)이고, `query.isOrderByChild(path)`는 읽기가 그 자식으로 정렬하는지 여부입니다(빈 세그먼트는 버려지며, 세그먼트가 없거나 잘못된 키인 경로는 오류).
- `http.encodeURL(s)`은 Java의 `URLEncoder.encode(s, "UTF-8")`이며 공백은 `%20`, 외톨이 서로게이트는 `?`로 인코딩합니다.
- 호출 없는 메서드 읽기(`auth.uid.contains`, `data.child`)는 null이 아니고 어떤 것과도 같지 않은 값입니다. 멤버가 아닌 호출 대상(`(c ? data.child : data.parent)('a')`)은, 해당 타입의 첫 번째 메서드가 Rules 로드 시 검사되므로, 그 타입이 메서드를 가지고 있으면 호출됩니다. 그 메서드가 받지 않는 인수 개수로 이런 값을 통해 호출하면 공식 에뮬레이터는 내부 오류(500)로 응답하지만 여기서는 거부됩니다.

마지막 세 항목에서 기록된 모든 형태에 대해 프로덕션은 공식 에뮬레이터와 같이 응답했습니다(두 프로필 모두 이를 따름).

### 대소문자 변환

- Java 21과 Fireemu의 더 새로운 Unicode 표가 대소문자를 다르게 매핑하는 문자를 포함한 문자열의 `toLowerCase()`와 `toUpperCase()`는 여기서 오류입니다. U+019B, U+0264, U+1C89, U+1C8A, U+A7CB부터 U+A7CF, U+A7D2부터 U+A7D5, U+A7DA부터 U+A7DC, 그리고 Basic Multilingual Plane 밖의 U+10D50부터 U+10D65, U+10D70부터 U+10D85, U+16EA0부터 U+16EB8, U+16EBB부터 U+16ED3입니다. 아래의 문맥 의존적 시그마 제한도 적용됩니다.
- `Σ`(U+03A3)를 포함한 문자열의 `toLowerCase()`는, `Σ`의 각 이웃이 문자열의 가장자리이거나, 공백이거나, 대소문자가 있는 라틴, 그리스, 키릴 문자(`'ΑΣ'`, `'ΑΣ Α'`)가 아니면 여기서 오류입니다. Java는 단어 경계로 어말 형태 `ς`를 선택하지만 Fireemu는 이를 재현하지 않으므로, `'Α:Σ'`와 `'ΑΣ.'`는 오류입니다.

### 잘못된 실시간 쿼리

잘못된 형식의 실시간 와이어 쿼리는 연결을 자동으로 끊거나 close 프레임을 보내지 않고 connection-error 제어 메시지를 받습니다. 이는 HTTP 400 응답이 아니라 실시간 프로토콜 응답입니다.

- 알 수 없는 필드, 문자열이 아닌 인덱스(`i`), 불리언이 아닌 포함 플래그(`sin`, `ein`), 문자열이 아닌 limit 방향(`vf`), 문자열이나 null이 아닌 바운드 이름(`sn`, `en`), 부동소수점 숫자로 쓴 limit(`2.0`도 포함)이 해당합니다.
- 대응하는 바운드나 limit이 없는 경우에도 플래그, 방향, 이름에 대한 타입 검사는 여전히 적용됩니다.
- null 바운드 이름은 이름이 없다는 뜻입니다. 그 외에 바운드 없이 유효한 포함 플래그와 이름, limit 없이 유효한 방향은 아무 효과가 없습니다.
- 지정된 정수 limit은 양수이며 부호 없는 32비트에 들어가야 합니다. 숫자가 아닌 limit과 그 범위를 벗어난 정수 limit은 대신 `invalid_parameters`를 받습니다.
- 지정된 limit에는 방향 `l` 또는 `r`도 필요합니다. 공식 에뮬레이터는 누락되거나 다른 방향을 어느 쪽도 아닌 것으로 읽을 수 있지만 Fireemu는 거부합니다.

### 그 밖의 차이

- 식별자의 `\uXXXX` 이스케이프는 공식 에뮬레이터가 읽는 방식대로 디코딩됩니다(`auth.uid`와 `auth.uid`는 `auth.uid`를 가리킴). 지원되지 않는 다른 JavaScript 구문은 Rules가 로드될 때 여전히 실패합니다.
- 공식 에뮬레이터가 요청에 내부 오류(500)로 응답하는 곳에서 Fireemu는 요청을 거부합니다. 예를 들어 스냅샷으로 판명되는 값에 대한 문자열 메서드(`(c ? root : 'a').length`), 그리고 공식 에뮬레이터가 경로로 읽을 수 없는 위치(`.`, `#`, `$`, `[`, `]` 또는 제어 문자가 있는 키, `.value`나 `.info` 같은 예약된 이름, 끝이 아닌 곳의 `.priority`, 32단계 또는 768바이트를 넘는 경로)의 `getPriority()`가 있습니다.
- 쿼리 매개변수를 두 번 이상 지정하거나 자격 증명(`auth`, `access_token`, `Authorization` 헤더)을 둘 이상 지정한 요청은 400으로 거부됩니다. 공식 에뮬레이터는 첫 번째 값을 취하며 `auth`를 다른 것보다 먼저 취합니다.
- 둘 다 거부하는 일부 규칙은 다른 메시지로 또는 다른 열에서 거부됩니다.
