## 연결

Functions를 실행하려면 코드베이스에 `firebase-functions` v6 또는 v7이 필요합니다.

```sh
# Only Functions (with Eventarc and Cloud Tasks); add the services your functions use,
# for example --only functions,firestore,auth
npx fireemu up --only functions

# All codebases declared in firebase.json, with the default services
npx fireemu up

# One codebase
npx fireemu up --only functions:<codebase>

# One directory, whatever firebase.json declares
npx fireemu up --functions ./functions
```

Functions는 기본적으로 `127.0.0.1:5001`에서 수신합니다(`--functions-port` 또는 `firebase.json`으로 변경할 수 있습니다). Web SDK가 이 주소를 가리키도록 설정합니다.

```js
import { getFunctions, connectFunctionsEmulator } from 'firebase/functions';
connectFunctionsEmulator(getFunctions(app), '127.0.0.1', 5001);
```

`fireemu exec` 아래에서는 `FIREEMU_FUNCTIONS_HOST`가 명령에 전달할 `host:port`를 담고 있습니다([환경 변수](../../reference/environment-variables/) 참고).

## 지원되는 트리거

다음은 Node.js `firebase-functions`의 export입니다. 트리거 유형별, export별 지원 현황은 [Functions 지원 인벤토리](https://github.com/fireemu/fireemu/blob/main/docs/functions-export-inventory.md)를 참고하십시오.

| 트리거 | v1 (`firebase-functions/v1`) | v2 (`firebase-functions/v2/*`) |
|---|---|---|
| HTTP 및 callable | `https.onRequest`, `https.onCall` | `onRequest`, `onCall`, `onCallGenkit` |
| Firestore | `firestore.document()` 이벤트 | `onDocumentCreated`, `Updated`, `Deleted`, `Written`, 그리고 `WithAuthContext` 변형 |
| Storage | `storage.object()` 이벤트 | `onObjectFinalized`, `Deleted`, `MetadataUpdated`, `Archived` |
| Pub/Sub | `pubsub.topic().onPublish` | `onMessagePublished` |
| 예약 | `pubsub.schedule()` | `onSchedule` |
| 태스크 큐 | `tasks.taskQueue().onDispatch` | `onTaskDispatched` |
| Authentication | `auth.user()` 이벤트, `beforeCreate`, `beforeSignIn` | `beforeUserCreated`, `beforeUserSignedIn`; `strict`에서는 `beforeEmailSent` |
| Realtime Database | `database.ref()` 및 `database.instance().ref()`의 `onCreate`, `onUpdate`, `onDelete`, `onWrite` | `onValueCreated`, `Updated`, `Deleted`, `Written` |
| Eventarc 및 알림 | | `onCustomEventPublished`, `onAlertPublished` |

이 중 여러 항목은 특정 조건에서만 실행됩니다. [트리거 관련 주의사항](#트리거-관련-주의사항)을 참고하십시오.

Realtime Database 트리거의 프로덕션 관찰 범위는 고정된 관리자 및 비인증 시퀀스, 그리고 REST와 웹 SDK를 통한 이메일/비밀번호 사용자의 12건의 쓰기입니다. 여기에는 상위 경로 쓰기와 다중 경로 쓰기, 호출 실패 후의 재전달이 포함됩니다. 전달 시점, 다른 공급자, 기록되지 않은 쓰기 또는 핸들러 형태는 검증되지 않은 상태로 남아 있습니다. 쓰기와 그 이벤트가 어떻게 수용되는지는 [로컬 Functions 트리거](../realtime-database/#로컬-functions-트리거)에서 설명합니다.

## 매개변수와 시크릿

`defineString`, `defineInt`, `defineBoolean`, `defineFloat`, `defineList`는 배포 시와 같은 방식으로 해석됩니다. 파일은 아래 순서로 적용되며 나중 파일이 앞선 파일을 덮어씁니다. 그다음에 매개변수의 `default`가 적용됩니다. 값도 기본값도 없는 매개변수가 있으면 `firebase deploy`가 같은 이유로 중단되기 때문에 코드베이스 시작을 거부하며, 이때 해당 매개변수와 값을 넣을 파일을 알려 줍니다. 시크릿(`defineSecret`)은 `.secret.local`에서 가져오며, 그것을 선언한 함수에만 전달됩니다.

| 파일(코드베이스 디렉터리 안) | 담는 내용 | 우선순위 | 배포 여부 |
|---|---|---|---|
| `.env` | 매개변수 값 | 가장 낮음 | 예, `firebase deploy`가 읽는 그대로 |
| `.env.<projectId>` (또는 `.env.<alias>`) | 한 프로젝트용 값 | `.env`보다 우선 | 예, 해당 프로젝트를 배포할 때 |
| `.env.local` | 로컬 실행용 값 | 가장 높음 | 배포되지 않음: 여기에만 있는 값은 프로덕션에서 누락됩니다. Fireemu와 공식 에뮬레이터가 적용합니다 |
| `.secret.local` | `defineSecret` 값 | 여기서 시크릿의 유일한 출처 | 배포되지 않음: 배포하려면 Secret Manager에 시크릿이 있어야 합니다 |
| `defineString` 등의 `default` | 대체 값 | 모든 파일보다 낮음 | 코드에 포함됨 |

- `.env.<projectId>`와 `.env.<alias>`가 모두 있으면 `firebase deploy`와 마찬가지로 시작이 중단됩니다.
- Fireemu는 Secret Manager에 접속하지 않습니다. 함수가 선언했지만 `.secret.local`에 없는 시크릿은 빈 문자열로 읽히며, 시작 시 경고가 해당 시크릿과 함수를 알려 줍니다.
- 두 프로필 모두에서, 이름이 `.secret.local`에 나타나는 상속된 환경 변수는 함수가 선언한 시크릿을 공급하기 전에 제거됩니다.
- `.runtimeconfig.json`을 읽는 코드베이스에는 이 파일이 `CLOUD_RUNTIME_CONFIG`로 코드에 전달됩니다. `firebase-functions` v7은 `functions.config()`를 제거했으므로 v7 코드베이스는 이를 읽지 않습니다.

## 함수를 호출할 수 있는 주체

`invoker`가 `"private"`이거나 서비스 계정 목록인 함수, 그리고 모든 태스크 큐 함수는 공개 URL로 오는 호출에 대해, 호출이 가진 자격 증명에 따라 다음과 같이 응답합니다.

| 공개 URL로의 요청 | 응답 |
|---|---|
| 자격 증명 없음 | 403. Cloud Run이 함수 실행 전에 거부하는 것과 같습니다 |
| Google이 발급한 ID 토큰 형태의 bearer(`iss`가 `https://accounts.google.com`인 JWT) | 통과. Fireemu는 Google에 ID 토큰을 확인할 수 없습니다 |
| 그 밖의 bearer. 로그인한 클라이언트 SDK가 보내는 Firebase Auth ID 토큰을 포함합니다 | 401. Cloud Run도 이를 받아들이지 않습니다 |

태스크 디스패치, Emulator UI, 제어 API(`POST /v1/sessions/default/functions/{name}:run`, 콘솔의 호출 및 큐 추가)는 공개 URL 호출이 아닙니다. UI와 제어 API는 프로젝트 소유자로서 동작합니다. `ingressSettings`는 기록되지만 강제되지 않습니다. `emulator` 프로필은 공식 에뮬레이터와 마찬가지로 모든 함수를 모든 호출자에게 제공합니다.

## callable의 App Check

callable 함수의 `enforceAppCheck`는 별도 설정 없이 동작합니다. 임의의 UUIDv4로 디버그 토큰 교환에서 토큰을 받아 `X-Firebase-AppCheck`에 담아 보내십시오.

- 토큰이 없거나 형식이 잘못된 일반 호출은 401로 거부됩니다. 정확한 v2 스트리밍 호출은 200 SSE 오류 레코드를 받습니다.
- 재사용(replay) 소비는 사용할 수 없습니다. `consumeAppCheckToken: true`인 Node callable에 유효한 토큰이 오면 `APP_CHECK_REPLAY_UNSUPPORTED`로 거부됩니다.
- Python callable은 [Python에 대해 설명된 검증과 제한](../functions-python/#프로덕션-및-firebase-cli와의-차이)을 따릅니다.

[App Check](../app-check/)를 참고하십시오.

### `strict`에서의 callable 자격 증명

`strict`에서는 데몬이 Node와 Python 모두에 대해 전달 전에 callable의 `Authorization`을 검증합니다.

| 호출의 `Authorization` | 결과 |
|---|---|
| 없음 또는 비어 있음 | 핸들러가 인증되지 않은 상태로 호출됩니다 |
| 비어 있지 않지만 검증된 프로젝트 사용자 ID 토큰이 아닌 자격 증명 | 핸들러 실행 전에 HTTP 401과 `application/json; charset=utf-8`로 거부되며, 본문은 `{"error":{"message":"Unauthenticated","status":"UNAUTHENTICATED"}}`입니다. 정확한 v2 스트리밍 요청은 대신 SSE 오류 레코드가 담긴 HTTP 200을 받습니다 |
| 여러 개의 `Authorization` 헤더 | 401 HTML 프런트엔드 페이지 |

유효한 프로젝트 ID 토큰을 보내거나 자격 증명을 생략하고, 중복된 헤더를 제거하십시오. 이는 매니페스트가 callable 코드를 `onRequest`로 제공하는 경우에도 적용됩니다. `onRequest(opts, onCall(...))`의 경우, 중첩된 callable 래퍼가 데몬이 검증하지 않은 자격 증명을 거부합니다. 일반 `onRequest` 핸들러는 원래 자격 증명을 그대로 계속 받습니다.

## 태스크 큐

태스크 큐 함수는 기록된 사례(TASK-QUEUE-FUNCTIONS)에 대해 검증되었으며, 알려진 차이는 [기록](https://github.com/fireemu/fireemu/blob/main/spec/compatibility/closure/TASK-QUEUE-FUNCTIONS.json)에 나열되어 있습니다. 데몬이 발급한 ID 토큰으로 이루어지는 strict 디스패치에서는 Node SDK가 `request.auth`를 구성하며, 핸들러와 그 타이머는 계속 `FUNCTIONS_EMULATOR="true"`를 봅니다. emulator 프로필은 `request.auth`를 설정하지 않은 채로 둡니다.

### 지연 태스크

`scheduleTime`(또는 `scheduleDelaySeconds`)과 함께 큐에 넣은 태스크는 Cloud Tasks와 마찬가지로 `strict`에서 그 시각까지 대기합니다. RFC 3339 형식이 아니거나 720시간보다 먼 `scheduleTime`은 400으로 거부됩니다. `emulator` 프로필은 공식 에뮬레이터와 마찬가지로 즉시 디스패치합니다.

기다리지 않고 지연 태스크를 테스트하려면 다음 중 하나를 수행하십시오.

- `functions.clock.tasks`를 `"virtual"`로 설정하고 시계를 이동합니다([시간과 예약 함수](../../guides/time/) 참고).
- 대기 중인 태스크를 해제합니다. Emulator UI의 Functions 페이지에는 대기 중인 태스크가 예정 시각과 **Run now** 버튼과 함께 표시됩니다. 제어 API에서는 `POST /v1/sessions/default/functions/{queue}:run`(대기 중인 모든 태스크) 또는 같은 경로에 `{"task": "<task id>"}`를 보내면(태스크 하나) 됩니다.

해제된 태스크에도 속도 제한과 동시성 제한은 계속 적용됩니다.

### `getTask`로 태스크 읽기

`strict`에서 `getTask`는 대기 중, 실행 중, 재시도 중인 태스크를 반환합니다.

- 기본값인 `responseView=BASIC`은 요청 본문을 생략하고, `responseView=FULL`은 원래 바이트를 base64로 반환합니다.
- 대기 중 응답은 두 프로덕션 기록과 마찬가지로 값이 0인 디스패치 횟수와 응답 횟수를 생략합니다.
- 최근에 완료되었거나 삭제된 이름은 기록된 최근 태스크 404 메시지를 반환하며, 알 수 없는 이름은 일반적인 not-found 응답을 유지합니다.
- 최근 조회 이력은 기존 이력 상한으로 제한되며, 이름을 즉시 재사용할 수 있는 경우 1시간 동안 유지되고, 그렇지 않으면 설정된 이름 보존 기간을 따릅니다.

FULL 보기, 활성/재시도 관찰, 잘못된 보기, 알 수 없는 이름에 대한 GET 응답, 이력 만료는 로컬에서는 테스트했지만 기록되지는 않았습니다. `getTask`의 완전한 동등성은 주장하지 않습니다.

### 속도 제한과 버스트

태스크를 수락하면 필요한 경우 해당 함수의 러너가 시작됩니다. `strict`에서 토큰 보충은 나노초 단위의 정수 주기를 사용하며 토큰 시점과 스케줄 시점에 깨어납니다. 동시에 도래하는 120개 태스크의 프로덕션 기록에서는 rate 1일 때 시작 버스트가 10이었고, rate 500은 버스트 100으로 읽혔습니다. 다른 rate는 비어 있는 상태로 시작하며 정수 토큰 용량은 `floor(max(rate, 1.1))`입니다. 이들의 프로덕션 버스트는 기록되지 않았습니다.

`emulator` 프로필은 1초 단위 갱신을 유지하며, firebase-tools 15.28.2와 같이 큐에 넣을 때의 정확한 이름으로 태스크를 삭제합니다. 이미 디스패치된 태스크도 한 번은 삭제할 수 있습니다.

### 디스패치 헤더와 본문

`strict`에서 `X-CloudTasks-QueueName`은 접두사가 없는 큐 ID이고, `X-CloudTasks-TaskETA`는 소수점 아래 6자리의 Unix 초이며, `User-Agent`는 `Google-Cloud-Tasks`입니다. 태스크가 제공한 헤더는 이 user agent나 `X-CloudTasks-*`, `X-Google-*`, `X-AppEngine-*` 계열을 덮어쓸 수 없습니다. `emulator` 프로필은 공식 에뮬레이터의 내부 큐 이름과 헤더 덮어쓰기를 유지합니다.

태스크 디스패치는 JSON 멤버 순서와 공백을 포함해 큐에 넣은 본문의 바이트를 그대로 보존합니다. strict 프로필은 빈 본문, JSON이 아닌 본문, 바이너리 본문 바이트도 수락하며, emulator 프로필은 JSON만 수락하는 방식을 유지합니다. 제공된 본문을 처리할 수 있는지는 여전히 핸들러가 판단합니다.

### `createTask`와 `deleteTask`

`strict`에서 `createTask`와 `deleteTask`는 각각 122단계로 이루어진 두 번의 기록(2026-11-11)에서 Cloud Tasks가 응답한 방식대로 응답합니다.

- 응답은 Task 자체입니다. `BASIC` 또는 `FULL` 보기, 19자리 숫자로 생성된 이름(프로덕션은 19자리 또는 20자리였습니다)이며, 과거의 `scheduleTime`은 현재 시각이 됩니다.
- 오류는 `google.rpc` JSON 오류이며, 프로덕션의 검사를 프로덕션의 순서로 수행합니다. 알 수 없는 필드, `payload_type`, 태스크 이름과 id, 15초에서 30분 사이의 `dispatchDeadline`, 최대 720시간 후까지의 `scheduleTime`, 최대 1 MiB의 태스크 순입니다.
- 큐에 있는 태스크의 이름은 409로 거부됩니다.
- 재시도는 데드라인 이후 `X-CloudTasks-TaskPreviousResponse: 504`를 싣고, 먼저 큐의 `minBackoff`만큼 기다립니다.
- 응답은 Cloud Tasks가 출력한 형태 그대로 출력됩니다. 같은 필드 순서의 여러 줄 JSON, `application/json; charset=UTF-8`, 인자 오류의 `details`입니다.
- `oidcToken`을 지정한 태스크에는 세 구간으로 된 `Authorization: Bearer` 토큰이 전달되므로, 핸들러에서 `request.auth`가 존재합니다. 이 토큰은 에뮬레이터가 발급하고 서명되지 않으며, 그 클레임은 Google의 것이 아닙니다.

네 가지 설정은 개발용 기본값이며, `productionExact`가 이를 프로덕션 값으로 설정합니다. 명시적으로 지정한 키는 `productionExact`보다 우선합니다. [프로필](../../guides/profiles/)을 참고하십시오.

| 설정 | 개발 기본값 | 프로덕션 |
|---|---|---|
| `functions.taskNameReuse` | 끝난 태스크의 이름을 즉시 사용할 수 있음 | 프로덕션 모드는 최대 3600초 동안 이를 거부함 |
| `functions.taskDispatchDeadlineSeconds` | 생략하거나 `"0s"`로 설정하면 60초 | 프로덕션의 기본값은 600 |
| `functions.taskRetryDefaults` | 3회 시도 | 프로덕션의 기본 큐는 총 100회 시도를 허용함 |
| `functions.taskRetryBackoff` | | 프로덕션의 재시도 간격은 십여 번 실패한 뒤 선언된 최댓값을 넘어서 늘어남 |

완료된 이름의 이력은 모든 큐를 통틀어 65,536개 이름과 큐 및 태스크 이름 텍스트 8 MiB로 제한됩니다. 둘 중 하나라도 초과하면 가장 오래된 이름부터 제거되며, 3600초 창이 끝나기 전에도 제거될 수 있습니다. 이 제한은 `"retained"` 모드에도 적용됩니다.

### 진행 중인 작업이 정리될 때까지 대기

진행 중인 작업이 정리되기만 하면 되는 테스트에는 `POST /v1/sessions/default:awaitIdle`에 `{ "scope": "runnable" }`을 보내십시오(v0.26.0부터). 이 범위에서는 미래의 스케줄과 재시도 백오프가 대기를 막지 않습니다. rate/동시성 때문에 대기 중인 도래한 태스크와 활성 HTTP 요청은 여전히 대기를 막습니다. 범위를 생략하면 모든 작업을 기다립니다. [실행 가능한 작업 대기](../../guides/test-worlds/#실행-가능한-작업-대기)를 참고하십시오.

## 예약 함수

스케줄은 Fireemu의 가상 시계 위에서 실행됩니다. `daemon.clockStart`로 시작 시각을 고정하지 않으면 이 시계는 실제 시간을 따르므로 시간이 흐르면서 발생 시점이 도래합니다. 시작 시각을 고정하면 시계가 멈춰 있으며, 발생 시점이 도래하게 하려면 시계를 이동합니다. [시간과 예약 함수](../../guides/time/)를 참고하십시오.

### 지금 실행

기다리지 않고 예약 함수를 실행하거나 지연 태스크를 해제하려면 다음을 사용합니다.

| 항목 | 예약 함수 | 태스크 큐 함수(`scheduleTime`을 기다리는 태스크) |
|---|---|---|
| Emulator UI, Functions 페이지 | 즉시 실행하거나, 시계를 다음 발생 시점으로 진행 | 대기 중인 태스크가 예정 시각과 **Run now** 버튼과 함께 표시됨 |
| 제어 API | `POST /v1/sessions/default/functions/{name}:run` | 같은 경로로 대기 중인 모든 태스크를 해제하며, `{"task": "<task id>"}`를 보내면 하나를 해제함(알 수 없는 id는 404) |
| 가상 시계 | `daemon.clockStart`를 고정하거나 `daemon.clock = "frozen"`으로 설정한 뒤 `{"seconds": 86400}`(`{"millis": n}`, `clock:advanceTo`, `clock:set`도 가능)와 함께 `POST /v1/sessions/default/clock:advance`를 호출하거나, Runtime 페이지를 사용 | `functions.clock.tasks = "virtual"`로 설정한 뒤 시계를 이동 |

제어 API는 UI 포트에 있지 않습니다. 그 주소는 시작 출력의 `control API:` 줄에 나옵니다. Authentication이 실행 중이면 Authentication 포트(기본값 9099)이고, 그렇지 않으면 다른 포트입니다. `fireemu exec` 아래에서는 `$FIREEMU_CONTROL_URL`이며 `Authorization: Bearer $FIREEMU_CONTROL_TOKEN`을 사용합니다(토큰은 `network.allowNonLoopbackHosts`가 설정된 경우에만 필요합니다). 예를 들어 `fireemu up`을 사용하면 다음과 같습니다.

```sh
curl -X POST http://127.0.0.1:9099/v1/sessions/default/functions/nightly:run
# {"enqueued":true,"function":"nightly"}
curl -X POST http://127.0.0.1:9099/v1/sessions/default/clock:advance -H 'content-type: application/json' -d '{"seconds": 86400}'
```

알 수 없거나 예약되지 않은 이름은 `400 INVALID_ARGUMENT`로 응답합니다. 수동 실행은 다음 발생 시점을 소비하지 않습니다. [예약 함수를 지금 실행](../../guides/time/#예약-함수를-지금-실행)을 참고하십시오.

`strict`에서 1세대 스케줄의 `firebase-schedule-<function>-<region>` 토픽에 메시지를 게시하면 핸들러도 호출되며, 원래의 Pub/Sub 데이터, 속성, ordering key, 메시지 ID가 보존됩니다. 일반적인 예약 발생 시점과 수동 실행은 여전히 한 번만 핸들러를 호출합니다.

## 이벤트 큐가 가득 찼을 때

런타임은 전달되지 않은 이벤트를 최대 4096개(페이로드는 64 MiB)까지 보관합니다. 들어가지 않는 이벤트는 조용히 사라지지 않으며, 어떻게 되는지는 이벤트의 출처에 따라 다릅니다.

- **Firestore, Storage, Pub/Sub 에뮬레이터, 제어 Pub/Sub 게시:** 쓰기 또는 게시가 거부되며 아무것도 전달되지 않습니다. 제어 게시는 `429 RESOURCE_EXHAUSTED`로 응답합니다.
- **Authentication:** 사용자 생성 또는 삭제는 어느 쪽이든 커밋됩니다. 해당 이벤트는 제한된 큐에 보관되었다가 용량이 돌아오면 오래된 순으로 전달됩니다. 보관된 이벤트가 4096개를 넘는 적체가 있을 때만 하나가 버려지며, 이 버려짐은 집계되고 로그로 남습니다.

<details>
<summary>세부 사항</summary>

- Firestore, Storage, Pub/Sub 에뮬레이터, 제어 Pub/Sub 게시(`POST /v1/sessions/{session}/pubsub/topics/{topic}:publish`)는 먼저 전체 팬아웃을 예약합니다. 즉 구독한 모든 함수에 대한 모든 메시지를, `duplicate` 장애가 요구하는 사본 수까지 포함해서 예약합니다. 전체가 들어가지 않으면 쓰기 또는 게시가 거부되며(제어 게시는 `429 RESOURCE_EXHAUSTED`로 응답하고 메시지 id를 발급하지 않습니다) 아무것도 전달되지 않습니다.
- 생성되거나 삭제된 Auth 사용자는 큐에 여유가 있든 없든 커밋됩니다. 프로덕션도 함수가 밀려 있다는 이유로 가입을 거부하지 않기 때문입니다. 큐가 아직 받을 수 없는 이벤트는 보관되었다가 용량이 돌아오면 오래된 순으로, 통째로 전달됩니다. `GET /v1/sessions/{session}/functions`는 보관된 개수를 `authEventsPending`으로 보여 주며, `await-idle`은 이 이벤트들이 비워지기를 기다립니다. 최대 4096개의 이벤트가 보관되며, 그 이상은 하나씩 버려지고 리소스 보고서에 `admission.auth_event_dropped`로 집계되며 로그로 남습니다. 세션 리셋은 보관된 이벤트를 나머지 큐와 함께 폐기합니다.

</details>

## 러너 출력

함수 로그와 러너의 표준 오류는 로컬 로그로 전달됩니다. 러너가 시작 핸드셰이크 전에 종료되면, 진단 정보에 종료 상태, 캡처된 표준 오류, 표준 출력의 제한된 끝부분도 포함됩니다. 애플리케이션이 쓴 출력에서 임의의 시크릿이 자동으로 가려지지는 않습니다. 함수 코드에서 자격 증명을 출력하거나 환경을 덤프하지 마십시오.

## 소스 리로드

Node 및 Python 코드베이스는 소스 변경을 자동으로 다시 불러옵니다.

- 이미 수락된 호출은 호출 데드라인의 범위 안에서 선택된 세대에서 끝까지 실행됩니다. 끝나지 않는 은퇴한 세대는, 디버거 모드를 제외하고, 마지막 미완료 호출의 데드라인으로부터 1초 뒤에 중지됩니다.
- 감시자의 첫 스캔 이전의 편집도 감지되며, 리로드 스냅샷은 종료 시 제거됩니다.
- 발견된 트리거 매니페스트를 변경하려면 Fireemu를 다시 시작해야 합니다. 거부된 리로드는 보통 이전 세대를 유지합니다.
- Node에서는 고정된 `--inspect-functions <port>`가 예외입니다. 교체본이 해당 포트를 바인드하려면 이전 러너가 먼저 중지되어야 합니다.
- Python은 inspector 옵션을 무시하며, 리로드가 실패하면 이전 세대를 유지합니다. Python 가상 환경은 원래 코드베이스에 연결된 채로 남으므로, 설치된 의존성을 바꾼 뒤에는 다시 시작하십시오. Python 바이트코드 캐시는 감시와 리로드 스냅샷에서 제외됩니다.

Windows에서는 소스 또는 로컬 시크릿 파일을 복사하기 전에 보호된 DACL로 리로드 스냅샷이 만들어집니다. Fireemu는 스냅샷 디렉터리, 임시 상위 디렉터리, 조상 디렉터리에 안전하지 않은 권한이나 재분석 지점(reparse point)이 있는지 확인하며, 30초 안에 검증할 수 없으면 스냅샷을 거부합니다. 이를 위해 Windows PowerShell이 필요합니다. [문제 해결](../../guides/troubleshooting/)을 참고하십시오.

## 프로세스 격리 (`functions.isolation`)

프로덕션은 모든 함수를 각자의 인스턴스에서 실행합니다.

- 함수의 정체성(`FUNCTION_TARGET`, `FUNCTION_SIGNATURE_TYPE`, `K_SERVICE`)과 함수가 선언한 시크릿이 처음부터 환경에 들어 있습니다.
- 자체 모듈 그래프를 가집니다.
- 2세대 인스턴스는 그 함수 하나에 대한 호출을 한 번에 최대 `concurrency`개까지 처리합니다(1세대는 하나만 처리합니다).
- 인스턴스는 첫 요청에서 시작됩니다.

`functions.isolation`은 실행이 이를 얼마나 가깝게 따를지 선택합니다.

| `functions.isolation` | 프로세스 | 의미 |
|---|---|---|
| `"codebase"` (기본값, `productionExact`는 예외) | 코드베이스당 러너 프로세스 하나 | 시작 비용이 가장 낮습니다. 함수들이 하나의 모듈 그래프를 공유하므로 모듈 수준 상태, 캐시, 싱글턴이 모든 함수에 보입니다. 프로세스 환경도 공유합니다. `FUNCTION_TARGET`, `FUNCTION_SIGNATURE_TYPE`, `K_SERVICE`는 가장 최근에 시작된 호출의 이름을 나타내므로, 다른 함수가 호출된 동안 `await` 이후에 이 값을 읽는 함수는 다른 함수를 보게 됩니다. `.secret.local`의 로컬 시크릿을 사용하는 호출은 단독으로 실행되므로, 배포된 함수라면 가졌을 동시성도 가려집니다. 시크릿은 사용자 코드가 로드되는 동안과 호출이 실행되는 동안, 그것을 선언하지 않은 모든 함수에서 가려집니다. |
| `"function"` (`productionExact`에서의 기본값) | 각 코드베이스의 함수당 러너 프로세스 하나 | 프로덕션의 형태입니다. 각 프로세스는 코드베이스를 스스로 로드하고, 해당 함수의 정체성과 그 함수가 선언한 로컬 시크릿이 이미 환경에 들어 있는 상태로 시작하며(따라서 이를 읽는 모듈 수준 코드가 값을 봅니다), 그 함수만을 함수에 설정된 동시성으로 처리합니다. 호출마다 다시 쓰거나 가리거나 큐에 넣는 것은 없습니다. 한 함수의 프로세스가 죽거나 재시작해도 다른 함수에는 영향이 없습니다. |

```json
{ "schemaVersion": 1, "functions": { "isolation": "function" } }
```

### `"function"`이 프로세스를 시작하는 방식

`"function"`에서 Fireemu는 먼저 코드베이스의 export를 읽는 디스커버리 프로세스를 시작했다가 다시 종료합니다. 그다음 함수 자체의 프로세스는 프로덕션 인스턴스처럼 그 함수에 대한 첫 요청, 이벤트, 태스크에서 시작됩니다. 그동안 도착한 작업은 프로세스를 기다렸다가 순서대로 한 번 전달됩니다. 콜드 스타트 때문에 이벤트가 버려지거나 순서가 바뀌는 일은 없습니다.

다음 두 종류의 함수는 대신 코드베이스와 함께 시작됩니다.

- Blocking Auth 함수. 가입이 짧은 데드라인 안에서 콜드 스타트 비용을 치러서는 안 되기 때문입니다.
- `--inspect-functions`가 주어졌을 때의 모든 함수. 각 프로세스가 디버거 포트를 미리 보고하도록 하기 위해서입니다.

프로세스는 한 번 시작되면 계속 유지되며, 유휴 프로세스를 중지하는 기능은 아직 없습니다. 프로세스가 종료된 함수는 코드베이스 프로세스와 마찬가지로 다음 사용 시 다시 시작됩니다. 소스 리로드는 코드베이스의 모든 프로세스를 함께 교체하며, 리로드로 코드베이스가 제공하는 함수가 달라지면 거부되고 이전 프로세스들이 계속 실행됩니다. 모든 프로세스의 로그 줄은 코드베이스 프로세스와 마찬가지로 전달되며, 제어 API의 상태에는 프로세스마다 `function`과 `started` 여부가 담긴 항목이 하나씩 나열됩니다. Python 코드베이스에도 적용됩니다.

### 비용

사용되는 함수마다 프로세스 하나와 로드된 코드베이스 사본 하나가 필요합니다. Node 24와 `firebase-functions` 7을 쓰는 노트북에서 측정했습니다(상주 메모리는 각 프로세스의 공유 페이지를 포함해 세므로 실제 합계보다 과대평가됩니다).

| 코드베이스 | `"codebase"` | `"function"`, 모든 함수 시작 |
|---|---|---|
| 함수 10개 | 시작 및 종료에 1.3초, 121 MiB, 프로세스 1개 | 2.5초, 1.2 GiB, 프로세스 10개 |
| 함수 22개 | 1.0초, 126 MiB, 프로세스 1개 | 3.0초, 2.7 GiB, 프로세스 22개 |

프로세스는 첫 사용 시에 시작되므로, 소수의 함수만 건드리는 실행은 그 함수들에 대해서만 비용을 치르며, 각 함수의 첫 호출은 콜드 스타트(약 1초)를 치릅니다. 모든 함수를 호출하는 테스트 스위트는 결국 오른쪽 열에 도달합니다. 이 때문에 개발과 CI에서는 `"codebase"`가 기본값으로 유지되며, `productionExact`는 `"function"`을 선택합니다.

### `"function"`이 거부되는 경우

- 코드베이스에서 제공하는 함수가 64개를 넘는 경우. `functions.isolation`을 기본값인 `"codebase"`로 설정하면 하나의 프로세스에서 제공합니다.
- `functions.runner`와 함께 명시적으로 쓴 경우(사용자 지정 러너 명령은 코드베이스당 한 번 시작됩니다).
- 고정된 `--inspect-functions <port>`와 함께 명시적으로 쓴 경우(프로세스들이 포트를 공유할 수 없습니다. 포트 없이 `--inspect-functions`를 쓰면 각 프로세스가 자기 포트를 갖습니다).

`productionExact`만이 `"function"`을 선택한 경우, 마지막 두 경우는 거부하는 대신 `"codebase"`를 사용합니다. 명시적인 `functions.isolation = "codebase"`는 항상 우선합니다.

## 디버깅

`--inspect-functions`로 Functions 러너를 Node inspector 아래에서 실행합니다.

```sh
npx fireemu up --inspect-functions 9229
```

## 고정된 함수 목록 제공 (`functions.manifest`)

`functions.manifest`는 디스커버리가 보고하는 제공 대상 집합을 대체하는 JSON 파일을 지정합니다. 이 파일은 `functions` 배열을 담습니다. 각 항목에는 `name`과, `type`이 `http`, `firestore`, `database`, `storage`, `pubsub`, `schedule`, `auth`, `blockingAuth`, `tasks`, `eventarc` 중 하나인 `trigger`가 있고, 선택적으로 `region`, `generation`, `entryPoint`, `timeoutSeconds`, `retry`, `concurrency`를 가질 수 있습니다.

Fireemu는 여전히 코드베이스를 불러오고 디스커버리를 수행하므로 러너가 시작되고 코드가 검사됩니다. 제공되는 함수, 그 트리거 유형, 옵션은 파일에 따릅니다. 파일에서 빠진 export는 제공되지 않으며, 함수는 파일이 지정한 트리거로 제공됩니다.

```json
{
  "schemaVersion": 1,
  "profile": "strict",
  "functions": { "manifest": "manifest.json" }
}
```

```json
{
  "functions": [
    { "name": "hello", "trigger": { "type": "http", "callable": false } },
    {
      "name": "ping",
      "trigger": {
        "type": "http",
        "callable": true,
        "enforceAppCheck": false,
        "consumeAppCheckToken": "disabled"
      }
    }
  ]
}
```

`hello`(`onRequest`), `ping`(`onCall`), `worker`(`onTaskDispatched`)를 export하는 코드베이스에서는 `functions loaded: hello, ping`으로 시작하며 `worker`는 제공되지 않습니다. 이 키가 없으면 세 함수 모두 제공됩니다.

### 파일이 바꿀 수 있는 것과 없는 것

- 경로는 설정 파일이 어느 디렉터리에 있든 작업 디렉터리를 기준으로 읽습니다(표준 파일의 다른 파일 설정과 같습니다. [설정 파일](../../guides/configuration/) 참고). 파일이 없거나, JSON이 아니거나, 잘못된 항목을 담고 있으면 경로나 함수를 알려 주며 시작이 중단됩니다(`functions manifest manifest.json: No such file or directory`, `manifest: function "hello": unsupported trigger type "carrierpigeon"`). `strict`에서는 프로덕션이 거부하는 선언이 여기서도 거부됩니다.
- 코드베이스 하나에 적용됩니다. 여러 개를 불러오는 실행은 시작을 거부합니다(`functions.manifest replaces discovery for one codebase, and this run loads 2 (a, b); name the one to load with --only functions:<codebase> or drop functions.manifest`).
- 파일은 코드가 무엇인지를 바꿀 수 없습니다. 파일에 있는 Blocking Auth 함수는 디스커버리가 찾은 것과 일치해야 하며, 그렇지 않으면 시작이 거부됩니다(`... invents Blocking Auth hook ... it must match codebase discovery`).
- [App Check](../app-check/)가 활성인 동안(`strict`의 기본값, `emulator`에서는 `appCheck.enabled: true`, `appCheck.enabled`가 `false`일 때는 비활성), 파일은 callable이 취급되는 방식도 바꿀 수 없습니다. 다음은 시작 시 거부됩니다.
  - `"callable": false`로 나열된 callable, 또는 `"callable": true`로 나열된 `onRequest` 함수
  - 태스크 큐, blocking 함수, 이벤트 트리거로 나열된 callable(`... declares "ping" as a non-HTTP function, but the codebase declares it callable ...`. 이 메시지는 이를 `callable: true`와 코드가 선언한 App Check 옵션을 가진 http 함수로 나열하거나, 파일에서 제거하거나, 태스크 큐로 의도한 것이라면 `onTaskDispatched`로 export하라고 안내합니다)
  - `enforceAppCheck` 또는 `consumeAppCheckToken`이 코드와 다른 callable
  - 코드베이스가 export하지 않는 HTTP 함수

### App Check가 꺼져 있을 때

App Check가 꺼져 있으면 위의 callable 검사는 실행되지 않고 Blocking Auth 일치만 적용됩니다. 잘못 표기된 항목이 가리키는 callable 래퍼에 도달하는 재정의는 없습니다.

- 러너는 토큰 검증을 건너뛰라는 지시를 받지 않습니다(그렇게 하는 것은 App Check 프로토콜뿐입니다).
- 데몬은 태스크 디스패치를 포함해 전달하는 모든 요청에서 에뮬레이터 내부의 인증 재정의 필드(`x-callable-context-auth`, `x-original-auth`)를 제거합니다.
- 래퍼의 토큰 검사는 Auth 에뮬레이터의 것이며, 태스크로 도달한 `onTaskDispatched` 함수에 대한 것과 똑같습니다.

`strict`에서는 이러한 큐로 보낸 태스크, 또는 파일이 `onRequest` 함수(`"callable": false`)로 나열한 callable로의 요청도 callable 요청이 통과하는 Bearer 검사를 통과해야 하므로(preflight와 자격 증명이 없는 요청은 해당하지 않습니다), 프로젝트 사용자가 아닌 Bearer는 코드가 실행되기 전에 401로 응답됩니다. 태스크의 경우 이는 디스패치 실패이며, 큐의 재시도 정책에 따라 포기할 때까지 재시도됩니다. 거부될 때마다 함수 이름(자격 증명은 절대 아님)을 담은 줄이 출력되며, 시작 시에도 그 함수를 지목하는 경고가 출력됩니다. 공식 에뮬레이터도 `functions.yaml`을 코드와 비교하지 않습니다.

## 프로덕션과의 차이

### 트리거 관련 주의사항

- **Realtime Database, 2세대.** 로컬 Realtime Database 인스턴스는 `us-central1`에 있으므로 다른 리전의 2세대 데이터베이스 트리거는 실행되지 않으며, 로드 시 경고가 이를 알려 줍니다.
- **Fireemu가 이벤트를 전달하지 않는 제품.** Data Connect(보류) 같은 제품의 트리거는 실행할 수 없습니다. 기본적으로 디스커버리는 이런 export가 있는 코드베이스를 거부하며(`functions.unservedTriggers = "refuse"`), `"report"`로 설정하면 각각을 보고하고 나머지를 불러옵니다. [Emulator UI](../../guides/ui/)의 Functions 페이지와 제어 API의 `GET /v1/sessions/default/functions`가 무시된 모든 export를 이유와 함께 나열합니다.
- **Remote Config.** 로컬 템플릿 관리로 클라이언트 템플릿을 게시하거나 롤백하면 2026-11-21에 프로덕션에서 기록한 형태의 이벤트가 v1 및 v2 핸들러에 전달됩니다. 검증 전용 요청과 거부된 요청은 아무것도 전달하지 않습니다. 서버 템플릿 게시는 이벤트를 전달하지 않습니다(프로덕션도 세 번의 기록에서 5분 안에 전달하지 않았습니다). 로컬 주입 액션은 계속 호출자가 제공한 메타데이터를 전달합니다.
- **Storage 아카이브 이벤트.** 버전 관리를 켠 버킷(`PATCH /storage/v1/b/{bucket}`에 `{"versioning":{"enabled":true}}`)에 대해서만 발생하며, 그 형태는 기록되지 않았습니다.
- **`beforeEmailSent`.** `strict`에서만 실행됩니다.

### 실행되지 않는 export

Fireemu가 제공할 수 없는 export(옵션을 해석하지 못하는 함수, 또는 인식하지 못하는 이벤트 유형)는 건너뜁니다. 각각은 시작 시 표준 오류에 `warning:`으로 출력되고 이어서 요약 줄이 나옵니다. 프로덕션이라면 배포되어 실행될 함수가 여기서는 실행되지 않으므로, "부작용 없음"을 단언하는 테스트가 엉뚱한 이유로 통과할 수 있습니다. 경고를 읽으십시오. `functions.unservedTriggers`는 여전히 Fireemu가 제공하지 않는 제품을 거부합니다.

### 프로덕션 검증

Node.js 코드베이스는 HTTP 및 callable 함수, 이벤트 트리거, 예약 함수에 대해 배포된 함수의 기록과 대조해 검증되었습니다. [호환성 표](../../compatibility/#프로덕션-검증)를 참고하십시오.

Python 코드베이스는 여섯 가지 이벤트 계열에 대해 별도의 검증 서술을 가집니다. Python 페이지의 [프로덕션 검증](../functions-python/#프로덕션-검증)을 참고하십시오.
