Fireemu는 두 종류의 파일을 읽습니다.

- **`fireemu.toml`**에는 [프로파일](../profiles/), Authentication 프로젝트 구성, 시계 등 Fireemu 자체의 설정이 들어 있습니다. `schemaVersion = 1`을 포함합니다. 같은 설정을 `fireemu.json`에 JSON으로 작성할 수도 있으며, 둘 다 있는 디렉터리는 거부됩니다([로드되는 파일](#로드되는-파일) 참조). [구성 스키마](../../reference/configuration/)를 참조하십시오.
- **`firebase.json`**은 Firebase CLI가 사용하는 파일입니다. Fireemu는 시작할 때마다 이 파일에서 포트, Security Rules, 인덱스, Functions 코드베이스를 읽습니다.

## 두 파일 함께 사용

Fireemu 고유의 설정은 `firebase.json`이 아니라 `fireemu.toml`에 두십시오. 두 파일을 함께 쓰려면 `fireemu.toml`에서 `firebase.json`을 지정합니다.

<Tabs syncKey="config-format">
<TabItem label="TOML">

```toml
#:schema https://raw.githubusercontent.com/fireemu/fireemu/v0.49.0/spec/config/fireemu.schema.json
# Configuration schema version: 1.
schemaVersion = 1
# Compatibility profile: "strict" or "emulator".
profile = "strict"
# Path to Firebase project configuration, relative to this file; a non-empty string.
firebaseJson = "firebase.json"
```

</TabItem>
<TabItem label="JSON">

```json
{
  "schemaVersion": 1,
  "profile": "strict",
  "firebaseJson": "firebase.json"
}
```

</TabItem>
</Tabs>

`npx fireemu init --firebase-json firebase.json`을 실행하면 이 내용이 자동으로 작성됩니다.

## 로드되는 파일

`up`, `exec`, `emulators:start`, `emulators:exec`는 다음 순서로 구성 파일을 선택합니다.

1. **명시적 플래그.** `--config <file>`과 `--firebase-json <file>`은 지정한 파일만 정확히 로드하며, 어떤 것도 검색하지 않습니다. `--config`는 `.toml` 경로(`.TOML`을 포함해 대소문자 구분 없음)를 TOML로, 그 밖의 모든 확장자를 JSON으로 파싱합니다. TOML 구성에는 반드시 `schemaVersion = 1`이 설정되어야 하며, JSON만 허용되는 `firebase.json`으로 읽히는 일은 없습니다. `--firebase-json`은 항상 JSON으로 읽습니다.
2. **현재 디렉터리의 Fireemu 구성.** 그렇지 않으면 현재 디렉터리에 있는 단일 `fireemu.toml` 또는 `fireemu.json`을 `--config`로 전달한 것처럼 로드합니다.
   - 두 파일이 모두 있으면 시작이 거부됩니다. 하나를 제거하거나 `--config`로 파일을 선택하십시오.
   - 이 파일의 `firebaseJson` 항목을 로드된 파일 기준으로 해석한 경로가 로드할 `firebase.json`입니다. `firebaseJson` 항목이 없는 `fireemu.toml` 옆의 `firebase.json`은 로드되지 않으며, 시작 출력에 그 사실이 표시됩니다.
   - 부모 디렉터리의 `fireemu.toml`이나 `fireemu.json`은 사용되지 않습니다. 그 안의 경로가 현재 디렉터리를 기준으로 하기 때문입니다.
   - 정규 파일 안의 상대 경로(`rules.source`, `storage.rules`, `functions.source`, `firestore.indexFile` 및 그 밖의 파일 설정)는 파일이 어느 디렉터리에 있든 작업 디렉터리를 기준으로 읽습니다. `firebaseJson`과 `firebase.json` 안의 경로만 해당 파일이 있는 디렉터리를 기준으로 읽습니다.
3. **가장 가까운 `firebase.json`.** 그렇지 않으면 가장 가까운 `firebase.json`을 `--firebase-json`으로 전달한 것처럼 로드합니다. Firebase CLI가 찾는 방식과 같이, 현재 디렉터리의 것을 우선하고 없으면 부모 디렉터리에서 처음 발견한 것을 사용합니다. 이 파일의 경로와 그 옆의 `.firebaserc`는 해당 디렉터리를 기준으로 읽습니다.
4. **내장 기본값.** 그렇지 않으면 내장 기본값이 적용되고 Security Rules는 로드되지 않습니다.

`--no-config-discovery`는 2단계와 3단계를 건너뜁니다. 시작 출력의 `config:` 줄에 로드된 파일이 표시됩니다.

검색에는 다음과 같은 효과가 있습니다.

- 프로젝트 ID는 검색된 `firebase.json` 옆의 `.firebaserc`에서 가져옵니다.
- 해당 파일의 에뮬레이터 포트, Hub, UI, 단일 프로젝트 설정이 적용됩니다.
- `functions` 항목이 있으면 Functions 런타임이 시작됩니다.
- `fireemu capabilities`는 검색된 `fireemu.toml`의 프로파일도 보고합니다.

테스트 옆의 `firebase.json`이 무시되던 이전 동작에 의존했다면 `--no-config-discovery`를 전달하십시오.

## 상대 경로

상대 경로는 어느 파일에 작성했는지에 따라 서로 다른 디렉터리를 기준으로 해석됩니다.

| 경로를 작성한 위치 | 해석 기준 |
|---|---|
| `fireemu.toml` 또는 `fireemu.json`: `rules.source`, `firestore.indexFile`, `storage.rules`, `functions.source` 및 그 밖의 파일 설정 | `fireemu`를 실행하는 작업 디렉터리 |
| `--functions <dir>` 및 그 밖의 경로 옵션 | 작업 디렉터리 |
| `fireemu.toml` 또는 `fireemu.json`의 `firebaseJson` | 해당 구성 파일이 있는 디렉터리 |
| `firebase.json` 안의 모든 경로(`firestore.rules`, `functions.source`, `hosting.public`, ...) | 해당 `firebase.json`이 있는 디렉터리 |

따라서 저장소 루트에서 `fireemu exec --config packages/api/fireemu.toml -- npm test`를 실행하면 `rules.source = "firestore.rules"`는 `packages/api`가 아니라 저장소 루트에서 읽습니다. Fireemu는 호환성을 위해 이 동작을 유지합니다. 이후 스키마 버전에서는 모든 경로를 구성 파일 기준으로 해석할 수도 있습니다.

이 차이를 피하려면 구성 파일이 있는 디렉터리에서 Fireemu를 실행하거나, 경로를 `firebaseJson`이 참조하는 `firebase.json`에 넣으십시오.

[`fireemu up --plan`](../../reference/cli/#실행-계획-확인)은 모든 경로에 대해, 실행이 여는 절대 경로와 그 경로를 해석한 기준 디렉터리를 보여 줍니다. 정규 구성의 경로가 구성 파일 자체의 디렉터리를 기준으로 했을 때와 다르게 해석되는 경우에는 경고합니다.

## 파일 소유권 검사

검색된 파일은 실행할 Functions 코드와 적용할 규칙을 지정할 수 있습니다. 그래서 Unix에서는 git이 저장소 소유권을 확인하는 것과 같이, 검색이 찾은 대상의 소유자를 확인합니다. Firebase CLI는 이를 확인하지 않습니다. Windows에서는 소유권을 확인하지 않습니다.

신뢰하는 소유자는 본인, root, 그리고 `sudo`로 root로 실행한 경우 `SUDO_UID`의 사용자입니다.

- **구성 파일.** 소유자를 신뢰할 수 없거나 모든 사용자가 쓸 수 있는 `fireemu.toml`, `fireemu.json`, `firebase.json`은 경고와 함께 건너뜁니다. 그룹 쓰기는 허용되므로 사용자 전용 그룹 umask(002, Debian과 Ubuntu의 기본값)에서 만든 파일은 로드됩니다.
- **`.firebaserc`.** 프로젝트와 타깃 별칭만 지정할 뿐 코드나 규칙은 지정하지 않으므로 소유자를 확인하지 않습니다. 이 파일이나 그 디렉터리를 모든 사용자가 쓸 수 있을 때만 건너뜁니다.
- **부모 디렉터리.** 소유자를 신뢰할 수 없거나 모든 사용자가 쓸 수 있는 부모 디렉터리(예: `/tmp`)에 이르기 전에 검색이 멈춥니다. 들어갈 수 없는 디렉터리처럼 검사할 수 없는 부모에서도 경고 없이 멈춥니다.
- **현재 디렉터리.** 사용자가 직접 선택한 곳에서 실행하므로 소유자를 확인하지 않습니다. 모든 사용자가 쓸 수 있는 현재 디렉터리는 전혀 검색하지 않습니다.
- **심볼릭 링크.** 심볼릭 링크는 그것이 가리키는 파일을 기준으로 판단합니다. 대상을 담은 디렉터리는 검사하지 않습니다.
- **읽기.** 각 후보는 한 번만 열립니다. 무엇이든 읽기 전에 열린 파일에서 소유자와 모드를 확인하고, 그 뒤 같은 파일에서 텍스트를 읽습니다. 검색된 파일이 16 MiB보다 크면 오류와 함께 거부됩니다.

건너뛴 파일이나 디렉터리는 경고에 이름이 표시되며, 실행은 아무것도 찾지 못한 것처럼 계속됩니다. 검색된 파일의 오류 메시지에는 검색이 해당 파일을 찾았다는 사실이 포함됩니다.

- 건너뛴 파일을 그래도 로드하려면 `--config` 또는 `--firebase-json`으로 지정하십시오.
- 경고를 없애려면 `--no-config-discovery`를 전달하십시오.

일반적인 두 구성에서 이 규칙에 걸립니다.

- **바인드 마운트된 체크아웃을 사용하는 root 컨테이너.** GitHub Actions의 `container:` 작업이나 root로 실행하는 `docker run -v "$PWD":/app` 같은 경우입니다. 파일의 소유자는 컨테이너의 root가 신뢰하지 않는 호스트 사용자입니다. 명시적 플래그를 사용하거나 체크아웃을 `chown`하십시오. `.firebaserc`는 여전히 프로젝트를 지정합니다. rootless Podman은 사용자를 컨테이너의 root로 매핑하므로 영향을 받지 않습니다.
- **`sudo`.** `SUDO_UID` 사용자 소유의 파일은 신뢰합니다.

## 구성 검증

`fireemu.toml`은 시작할 때 검증됩니다. Fireemu가 받아들이지 않는 값이 있으면 오류와 함께 중단됩니다.

- `up`, `exec`, `config show`는 두 형식 모두에서 스키마에 없는 키와 잘못된 타입의 값을 거부합니다. 오류에는 파일, 키, 기대한 타입이 표시됩니다. 예: `fireemu.toml: daemon.firestorePort must be an integer, found a string`.
- 정수 설정은 값이 정수에 해당하더라도 부동소수점을 거부합니다. 오류 메시지가 안내하듯 `8080.0`이 아니라 `8080`으로 작성하십시오.
- [구성 스키마](../../reference/configuration/)는 에디터에서도 사용할 수 있는 JSON Schema입니다.

구성이 어떻게 해석되는지는 두 명령으로 확인할 수 있습니다.

- `fireemu capabilities`는 구성이 해석된 프로파일의 capability manifest를 출력합니다.
- `fireemu up --plan`과 `fireemu exec --plan -- <command>`는 실행을 시작하지 않고, 파일, 명령줄, 환경에서 해석된 모든 내용(프로젝트, 서비스, 포트, 파일, Functions 런타임, 상속된 변수)을 출력합니다. [실행 계획 보기](../../reference/cli/#실행-계획-확인)를 참조하십시오.

## 레퍼런스 파일 생성

`fireemu init --reference`는 스키마에서 생성한 주석 달린 레퍼런스인 `fireemu.reference.toml`도 작성합니다. 기존 `fireemu.json`이 있으면 대신 `fireemu.reference.jsonc`를 작성하므로, 레퍼런스의 키가 구성 형식과 일치합니다. Fireemu는 이 파일을 로드하지 않습니다.

- 일반 `fireemu.toml`은 최소한으로 유지됩니다. 레퍼런스의 키를 여기에 복사하면 해당 키가 명시적으로 지정되므로 `productionExact`가 그 키를 전환하지 않게 됩니다.
- 레퍼런스에서는 다음 키가 주석 처리된 채로 남습니다. 기본값이 없는 키, 존재 자체가 동작을 선택하는 키, `productionExact`가 관리하는 키, 전방 호환성을 위해 허용되지만 현재 효과가 없는 키(주석에 그렇게 표시됨)입니다.
- `fireemu config lint --deny-ineffective`는 구성이 효과 없이 허용되는 키를 설정하면 CI 작업을 실패시킵니다. `--allow`와 `--allow-file`로 의도적으로 유지하는 키를 나열합니다([`config lint`](../../reference/cli/#config-lint) 참조).
- 초기화할 때 `--reference`를 `--profile` 또는 `--firebase-json`과 함께 사용할 수 있습니다. 기존 `fireemu.toml` 또는 `fireemu.json`이 있고 두 옵션이 모두 없으면 레퍼런스만 작성됩니다.
- 기존 출력 파일을 교체하려면 `--force`가 필요합니다.

### 스키마 주석

릴리스된 바이너리에서는 생성되는 스키마 주석이 GitHub 저장소에 있는 해당 릴리스의 스키마 파일(`https://raw.githubusercontent.com/fireemu/fireemu/v<version>/spec/config/fireemu.schema.json`)을 가리키므로, 에디터는 설치된 버전이 받아들이는 키를 기준으로 파일을 검사합니다. 소스에서 빌드한 바이너리(릴리스 사이의 빌드를 포함하며, 이 경우 해당 버전의 태그보다 새로운 스키마를 내장합니다)는 대신 `main` 위치를 기록합니다.

릴리스 태그, `main`, 또는 이전 `https://fireemu.dev/spec/config/fireemu.schema.json` 위치를 지정한 `$schema`나 `#:schema`도 여전히 로드됩니다. 에디터 검증을 위해서는 이전 주석을 실행 중인 버전의 태그로 교체하십시오.

Fireemu는 내장된 스키마로 검증하며 주석의 URL을 가져오지 않습니다. `fireemu config schema --out <path>`는 내장된 스키마를 파일로 기록하므로, GitHub에 접근할 수 없는 에디터나 도구에서 사용할 수 있습니다.

## TOML 값과 JSON null

TOML 파일은 JSON 파일과 같은 JSON Schema, 검증, 기본값을 사용합니다.

- Taplo나 Even Better TOML에서 스키마를 선택하려면 파일을 `#:schema https://raw.githubusercontent.com/fireemu/fireemu/v0.49.0/spec/config/fireemu.schema.json`(실행 중인 버전의 태그)으로 시작하십시오.
- 타임스탬프 값은 따옴표로 감싸십시오. 스키마에 datetime 타입이 없으므로 TOML datetime은 키 이름과 함께 거부됩니다.

TOML에는 `null`이 없습니다. 아래의 null 허용 설정은 모두 포함하는 테이블에서 키를 생략하고, null 허용 배열 항목은 항목을 생략하십시오. 존재 자체가 의도된 경우에는 포함하는 테이블이나 배열을 유지하십시오. 빈 배열과 빈 테이블의 기존 의미는 그대로입니다.

| null 허용 JSON 키 | null과 TOML 생략의 의미 |
|---|---|
| `limits.queryCatalog`, `firestore.textSearch.visibilityLag` | 허용되지만 런타임에는 아무 효과가 없습니다. 생략하면 이 키들의 명시적 값과 시작 시 안내도 함께 사라집니다. |
| `limits.firestorePlan.compositeIndexLimitOverride`, `limits.firestorePlan.singleFieldConfigLimitOverride`, `limits.firestorePlan.enterpriseIndexLimitOverride` | 재정의 없음. null이 아닌 재정의는 현재 거부됩니다. |
| `auth.providers`, `auth.providers.oidc`, `auth.providers.saml` | 공급자 시드 선언 없음. 빈 배열은 빈 대체 목록을 명시적으로 선언하는 것이며 생략과 다릅니다. |
| `auth.providers.oidc[].displayName`, `auth.providers.oidc[].clientSecret`, `auth.providers.saml[].displayName` | 선택적 공급자 값 없음. |
| `auth.authorizedDomains` | 시드 없음. 기본 도메인을 유지합니다. 빈 배열은 도메인이 없음을 선언합니다. |
| `auth.authorizedDomains[]` | 이 항목을 무시합니다. TOML 배열에서 빼십시오. |
| `auth.mfa`, `auth.multiTenant`, `auth.tenants` | 선언 없음. 해당하는 기본값을 유지합니다. |
| `auth.mfa.enabledProviders`, `auth.mfa.providerConfigs` | 선언된 MFA 구성에 이 종류의 공급자가 없음. MFA를 선언하는 경우 `auth.mfa` 테이블은 유지하십시오. |
| `auth.mfa.providerConfigs[].totpProviderConfig` | 이 공급자 항목을 무시합니다. 해당 항목에서 키를 생략하십시오. |
| `auth.mfa.providerConfigs[].totpProviderConfig.adjacentIntervals` | 선언된 TOTP 공급자에서 인접 간격 0을 사용합니다. 해당 테이블은 유지하십시오. |
| `auth.blockingFunctions.triggers.beforeCreate`, `auth.blockingFunctions.triggers.beforeSignIn` | 명시적 트리거 선택에서 이 트리거를 비활성화합니다. `[auth.blockingFunctions.triggers]`는 유지하십시오. 이 테이블 전체를 생략하면 대신 검색이 활성화됩니다. |
| `auth.quota.signUpQuotaConfig` | 가져온 재정의를 포함해 임시 할당량 재정의를 해제합니다. `[auth.quota]`는 빈 상태로 유지하십시오. quota 테이블 전체를 생략하면 가져온 재정의가 유지됩니다. |
| `auth.passwordPolicy.constraints.maxLength`, `auth.passwordPolicyOverrides[].passwordPolicy.constraints.maxLength` | 사용자 지정 최대 길이 없음. |
